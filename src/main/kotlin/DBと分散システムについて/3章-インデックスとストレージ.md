## 3.1 データは「ページ」単位で動く

### 1バイト欲しくても16KB読む

第1章の CSV では「1行ずつ読む」と考えていました。しかし DB は行単位では読み書きしません。**ページ**という固定長のブロック単位で扱います。InnoDB
では既定 **16KB** です。

```sql
SELECT @@innodb_page_size;
```

```
+--------------------+
| @@innodb_page_size |
+--------------------+
|              16384 |
+--------------------+
```

なぜ固定長のブロックなのか。理由は Phase 2 でやった話とまったく同じです。

- ディスク(SSDでも)は**ブロック単位**でしか読めない。1バイトだけ読む方法はない
- **1回のI/Oのコストが高い**ので、どうせ払うならまとめて読んだ方が得
- 固定長にすると、メモリ上の管理(キャッシュ、置き換え)が単純になる

つまり、**「1行取得する」と言っても、実際には最低16KB読んでいます。** 100バイトの行が欲しくても16KBです。この事実が、この章のあらゆる判断の土台になります。

> 🔗 **Phase 2 との接続**: OS のページ(通常4KB)とページキャッシュの話と同じ構造です。InnoDB
> はその上に自前で16KBのページ管理を持っている、という二層構造になっています。

自分のテーブルが何ページあるか見てみましょう。

```sql
SELECT table_name,
       table_rows,
       ROUND(data_length / 1024 / 1024)  AS data_mb,
       ROUND(index_length / 1024 / 1024) AS index_mb,
       data_length / 16384               AS data_pages
FROM information_schema.tables
WHERE table_schema = 'cs_study';
```

`orders` なら 50万行で 30MB 前後、ページ数にして 2,000 ページ弱でしょう。

**ここで大事な計算をします。**

```
1ページ 16KB に、1行 60バイト前後の orders は何行入るか?
16384 ÷ 60 ≒ 270行  (実際は管理領域があるので 200行程度)
```

つまり **1回のI/Oで200行取れます**。だから「全表走査は50万回のI/O」ではなく「**2,500回程度のI/O**」です。全表走査が思ったより速いのは、このためです。

そしてここから、第2章 2.6④の答えの半分が出ます。**インデックス経由で1行ずつ取りに行くと、1行ごとに別々のページを触る可能性がある
**。1000行取るのに1000回のI/Oを払うくらいなら、2,500回で全部読み切った方が安い、という判断があり得るわけです。

## 3.2 B+木 — なぜ100万行を3段で引けるのか

### まず「二分探索木ではダメ」を確認する

Phase 0 で木構造をやりました。100万件から1件探すなら、二分探索木で $\log_2 1{,}000{,}000 \approx 20$ 回の比較で届きます。効率的に見えます。

**しかしディスクでは破滅的です。** 二分探索木のノードは小さいので、20回の比較が **20回の別々のページ読み込み**
になります。1回のI/Oが仮に0.1msなら2ms。しかも各ノードが16KBのページを1つ占有するので、容量も無駄です。

**問題は「比較回数」ではなく「I/O回数」です。** ならば、1ページに詰め込めるだけキーを詰めて、**1回のI/Oで一気に絞り込む**べきです。

これが B+木の発想です。

### B+木の形

```
                    [ 根ノード ]
                    100 | 500 | 900        ← キーと子への位置だけ(データは持たない)
                   /     |      \
          ┌───────┘      │       └────────┐
     [内部ノード]   [内部ノード]     [内部ノード]
      120|150|...    520|560|...     910|950|...
        /  |  \        /  |  \         /  |  \
     [葉] [葉] [葉]  [葉] [葉] [葉]  [葉] [葉] [葉]   ← ここに実データ(または主キー値)
      ←→   ←→   ←→   ←→   ←→   ←→   ←→   ←→        ← 葉同士が横に連結されている
```

二分探索木との違いは3つです。

**① 1ノードに大量のキーが入る**
子への分岐が2本ではなく、**1000本前後**あります。これを**扇出(fan-out)**と呼びます。

**② データは葉にしかない**
内部ノードは「道案内」専用で、キーと子ページの位置だけを持ちます。データを持たないので、**その分だけ多くのキーを詰められます
**。これが B木(B-tree)と B+木の違いで、InnoDB が使っているのは **B+木**です。

**③ 葉が横に連結されている**
`WHERE id BETWEEN 100 AND 200` のような範囲検索で、**木を降りるのは最初の1回だけ**。あとは葉を横に辿ります。`ORDER BY id`
が速いのもこの構造のおかげです。

### 扇出と段数を計算する

実際に数字を入れます。**この計算を一度やっておくと、インデックスの感覚が体に入ります。**

**内部ノード1ページに何個のキーが入るか**

```
1エントリ = キー(BIGINT 8バイト)+ 子ページ番号(6バイト) = 14バイト
使えるページ領域 ≒ 16384 × 0.93 ≒ 15,200バイト
エントリ数 = 15,200 ÷ 14 ≒ 1,085
```

**約1,000本に枝分かれします。**

**葉ページに何行入るか**(クラスタインデックス = 行そのものが入る場合)

```
orders の1行 ≒ 60バイト(+行ヘッダ等で実質80バイト程度)
15,200 ÷ 80 ≒ 190行
```

**では、何段でどれだけ格納できるか**

| 段数      | 葉ページ数     | 格納できる行数    |
|---------|-----------|------------|
| 1段(根が葉) | 1         | 約190行      |
| 2段      | 1,000     | 約19万行      |
| 3段      | 1,000,000 | **約1.9億行** |
| 4段      | 10億       | 天文学的       |

**3段で1.9億行**です。つまり、

> **実務で扱うたいていのテーブルは、主キー検索が「3回のページ読み込み」で終わります。**
> しかも上の段(根・内部ノード)は頻繁に使われるので、**ほぼ確実にメモリに乗っています**。
> 結果、実際にディスクを触るのは**最後の1回だけ**。これが「1ms未満」の正体です。

第1章で `WHERE id = 999999` が計測不能なほど速かった理由が、これで説明できます。100万行だから遅い、ということが**起きない**
構造なのです。データが100倍になっても段数は1つ増えるだけです。

### 実際の段数を確かめる

自分のテーブルの木の形を覗いてみましょう。

```sql
SELECT index_name, stat_name, stat_value
FROM mysql.innodb_index_stats
WHERE database_name = 'cs_study'
  AND table_name = 'orders'
  AND stat_name IN ('size', 'n_leaf_pages');
```

```
+--------------------+--------------+------------+
| index_name         | stat_name    | stat_value |
+--------------------+--------------+------------+
| PRIMARY            | n_leaf_pages |       1580 |   ← 葉ページ数
| PRIMARY            | size         |       1583 |   ← 総ページ数
| idx_orders_user_id | n_leaf_pages |        520 |
| idx_orders_user_id | size         |        522 |
+--------------------+--------------+------------+
```

`size - n_leaf_pages` が内部ノードの数です。上の例では **3ページ**。1,580枚の葉を束ねるのに、根1枚+内部2枚で足りている、つまり
**3段**の木です(葉ページ1,580 ÷ 扇出1,000 ≒ 2 なので計算とも合います)。

50万行のテーブルが**わずか3段**。手元の値を確認してみてください。

> 📌 **ここまでのまとめ**
> インデックスが速い理由は「賢いアルゴリズム」ではなく、**「1回のI/Oで1,000分岐する木にしたから、I/O回数が3回で済む」**
> という、極めて物理的な話です。

## 3.3 クラスタインデックス — MySQL 最大の特徴

ここからが MySQL(InnoDB)固有の話で、**この章の核心**です。

### 主キーの木が、データ本体そのもの

InnoDB では、**テーブルのデータは主キーの B+木の葉に格納されています**。「テーブル」と「主キーインデックス」は別々のものではなく、
**同じ1本の木**です。これを**クラスタインデックス**と呼びます。

```
【主キー(クラスタ)インデックス】= テーブル本体
                [ 100 | 500 ]
                /            \
   [ id=1, user_id=42, status='paid', total=3000, ordered_at=... ]   ← 行の全部が入っている
   [ id=2, user_id=17, status='shipped', ... ]
   [ id=3, ... ]
```

一方、`user_id` のセカンダリインデックスはこうなっています。

```
【セカンダリインデックス idx_orders_user_id】
                [ 40 | 80 ]
                /          \
   [ user_id=42 → id=1 ]      ← インデックスの列 + 主キーの値 だけ!
   [ user_id=42 → id=8891 ]
   [ user_id=43 → id=77 ]
```

**セカンダリインデックスの葉には、行のデータが入っていません。** 入っているのは「インデックスに指定した列」と「**主キーの値**
」だけです。

### 帰結①: 二度引き(テーブルアクセス)

そのため、`SELECT * FROM orders WHERE user_id = 42` はこう動きます。

```
① セカンダリインデックスの木を降りる(3段)   → id = 1, 8891, ... が分かる
② その id ごとに、主キーの木を降りる(3段)   → 行の中身を取ってくる  ← 二度引き!
```

ヒットした行数だけ②が繰り返されます。**5行なら 3 + 5×3 = 18回**のページアクセス。

**これで第2章の謎が全部解けます。**

**謎1: なぜ「ヒットしすぎる範囲条件」だと全表走査が選ばれるのか(2.6④)**

10万行ヒットするなら、②が10万回走ります。しかも②の飛び先は**バラバラのページ**なので、ランダムアクセスです。一方、全表走査なら
2,500 ページを順番に読むだけ。

```
インデックス経由: 10万回のランダムページアクセス
全表走査:         2,500回のシーケンシャルアクセス
```

**全表走査の圧勝**です。オプティマイザは正しかったわけです。目安として、**返る行数がテーブルの2〜3割を超えるとインデックスは損
**になります(この閾値はコスト計算の結果で、固定値ではありません)。

**謎2: なぜ `Using index` が最高なのか**

②が**まったく発生しない**からです。次節で詳しくやります。

### 帰結②: 主キーは短くすべき

**主キーの値は、すべてのセカンダリインデックスの葉に埋め込まれています。**

```
主キーが BIGINT(8バイト)   → セカンダリの各エントリに 8バイト
主キーが VARCHAR(36)(UUID文字列)→ 各エントリに 約145バイト!
```

セカンダリインデックスが3本あって1000万行なら、この差は **数GB** になります。ディスクだけの問題ではありません。*
*バッファプールを圧迫し、キャッシュヒット率を下げます**(3.6)。

「主キーはメールアドレスにしよう」「複合主キーで自然キーにしよう」という設計は、MySQL では慎重に検討すべきです。

### 帰結③: 主キーの挿入順が性能を左右する

クラスタインデックスは主キー順に並んでいます。ということは、

**AUTO_INCREMENT の連番**

```
[... | 998 | 999 | 1000] ← 常に一番右の葉に追記される
```

追記だけなので、触るページは常に同じ1枚。**極めて効率的**です。ページは 15/16 程度まで詰めてから次へ進みます。

**UUID v4(ランダム)**

```
[ 3f2a... ] [ 8c91... ] [ a04d... ]  ← どこに挿さるか毎回バラバラ
```

3つの問題が同時に起きます。

1. **ページ分割**: 満杯のページの真ん中に挿入されると、ページが2つに割れます。半分ずつの隙間だらけのページが増える(
   =容量が1.5倍以上に膨らむ)
2. **ランダムI/O**: 挿入のたびに別のページを触るので、バッファプールに乗っていないページを読み込む必要がある
3. **キャッシュ効率の悪化**: 「最近挿入したデータ」がメモリ上の一箇所にまとまらない

実測では、**ランダムな主キーは連番の数倍から10倍遅くなる**ことがあります。

> 💼 **実務での落としどころ**
> 分散システムでは連番を避けたい事情があります(第7章のシャーディングで扱います)。その場合の解が **UUID v7 / ULID** です。*
*先頭に時刻を含むので、生成順にほぼ単調増加**します。ランダム性を保ちながら挿入位置を末尾に寄せられる、という設計です。
> どうしても UUID v4 が必要なら、せめて `BINARY(16)` で持ってください(`VARCHAR(36)` の半分以下)。

## 3.4 カバリングインデックス — 二度引きを消す

### `Using index` を狙って出す

二度引きが起きるのは「欲しい列がセカンダリインデックスに無い」からです。ならば、**欲しい列をインデックスに入れてしまえばいい
**。

実験しましょう。

```sql
CREATE INDEX idx_orders_user_id_amount ON orders (user_id, total_amount);

-- ① total_amount だけ欲しい
EXPLAIN
SELECT total_amount
FROM orders
WHERE user_id = 42;

-- ② 全列欲しい
EXPLAIN
SELECT *
FROM orders
WHERE user_id = 42;
```

```
①  type=ref  key=idx_orders_user_id_amount  Extra=Using index          ← 🎉
②  type=ref  key=idx_orders_user_id         Extra=NULL
```

①の `Using index` が**カバリングインデックス**の成立です。インデックスの葉に `user_id` も `total_amount` も入っているので、
**主キーの木を降りる必要がありません**。

行数が多いときほど差が出ます。

```sql
-- 大量にヒットさせて比較する
SELECT SQL_NO_CACHE SUM(total_amount)
FROM orders
WHERE user_id < 1000; -- カバリング
SELECT SQL_NO_CACHE SUM(id + total_amount)
FROM orders
WHERE user_id < 1000; -- 二度引き発生
```

**実行時間を測って記録してください。** 数倍の差が出るはずです。

### `SELECT *` が悪い理由

ここでようやく、よく言われる「`SELECT *` を書くな」の**技術的な理由**が言えます。

- 通信量が増えるから(これは副次的)
- **カバリングインデックスが成立しなくなるから**(これが本質)

不要な列を1つ含めるだけで `Using index` が消え、二度引きが復活します。**必要な列だけ書くと、インデックス設計の選択肢が広がる
**のです。

> ⚠️ **やりすぎ注意**: 「じゃあ全列をインデックスに入れよう」とすると、それはテーブルのコピーを作るのと同じです。インデックスが肥大化し、書き込みが遅くなり、バッファプールを食います。
**頻繁に実行される特定のクエリのために作る**のが正しい使い方です。

実験が終わったら消しておきます。

```sql
DROP INDEX idx_orders_user_id_amount ON orders;
```

## 3.5 複合インデックス — 列の順序がすべて

### 電話帳のたとえ

紙の電話帳は「**姓 → 名**」の順に並んでいます。

- 「田中」で始まる人を探す → ✅ できる
- 「田中 太郎」を探す → ✅ できる
- 「**太郎**という名前の人」を探す → ❌ **できない**(全ページ見るしかない)

複合インデックス `(姓, 名)` は、まさにこれです。**左端の列から順にしか使えません。左端一致の原則**と呼びます。

なぜか。B+木は**キーの並び順**で構成されていますが、その並び順は「まず姓で比較し、同じなら名で比較」という辞書順だからです。姓を無視すると、名はバラバラに散らばっています。

### 実験する

```sql
CREATE INDEX idx_orders_uid_at ON orders (user_id, ordered_at);

-- ① 左端だけ → 使える
EXPLAIN
SELECT *
FROM orders
WHERE user_id = 42;

-- ② 両方 → 使える(理想形)
EXPLAIN
SELECT *
FROM orders
WHERE user_id = 42
  AND ordered_at > '2026-01-01';

-- ③ 2番目だけ → 使えない
EXPLAIN
SELECT *
FROM orders
WHERE ordered_at > '2026-01-01';

-- ④ 順番を入れ替えて書いた → 使える(WHERE句の記述順は関係ない!)
EXPLAIN
SELECT *
FROM orders
WHERE ordered_at > '2026-01-01'
  AND user_id = 42;
```

③だけが `type = ALL` になります。**④が使えることに注目してください。** 重要なのは**インデックスの列順**であって、SQL
に書いた順ではありません。オプティマイザが並べ替えてくれます。

### `key_len` で「どこまで使ったか」を読む

第2章で保留にしていた `key_len` が、ここで意味を持ちます。**インデックスの何バイト目まで使ったか**を示します。

各型のバイト数:

| 型                              | バイト数          |
|--------------------------------|---------------|
| `BIGINT UNSIGNED NOT NULL`     | 8             |
| `DATETIME(6) NOT NULL`         | 8             |
| `INT NOT NULL`                 | 4             |
| `VARCHAR(20)` utf8mb4 NOT NULL | 20×4 + 2 = 82 |
| NULL を許可する列                    | 上記 **+1**     |

`(user_id, ordered_at)` なら合計16バイトです。

```
① WHERE user_id = 42                     → key_len = 8   (1列目だけ使用)
② WHERE user_id = 42 AND ordered_at > .. → key_len = 16  (2列とも使用) 🎉
```

**`key_len` が想定より小さい = インデックスを途中までしか使えていない**、という診断ができます。「複合インデックスを張ったのに速くならない」ときの確認ポイントです。

### 列順を決める原則

**「等値 → 範囲 → ソート」の順に並べる。** そして、

> ⚠️ **範囲条件を使った列より後ろの列は、絞り込みに使えません。**

これが一番重要なルールです。理由は電話帳で考えれば明らかです。「姓が『あ』〜『か』の範囲」で探すと、その中の名前はバラバラに散らばっているので、名で絞り込めません。

具体例で確認します。

```sql
SELECT *
FROM orders
WHERE user_id = 42
  AND status = 'paid'
  AND ordered_at > '2026-01-01';
```

| インデックス                          | 結果                                        |
|---------------------------------|-------------------------------------------|
| `(user_id, status, ordered_at)` | ✅ 3列すべて使える(等値2つ→範囲1つ)                     |
| `(user_id, ordered_at, status)` | ❌ `ordered_at` が範囲なので、`status` は絞り込みに使えない |

**同じ3列でも、順序で性能が変わります。**

### ソートを消す

`ORDER BY` をインデックスで解決できると、`Using filesort` が消えます。

```sql
-- インデックスなしの状態(第2章 2.6⑤ の再訪)
EXPLAIN
SELECT *
FROM orders
WHERE user_id = 42
ORDER BY ordered_at DESC LIMIT 10;
```

`idx_orders_uid_at` があれば、`Extra` から **`Using filesort` が消えます**。木の中で `user_id = 42` の範囲は既に
`ordered_at` 順に並んでいるので、**その末尾から10件取るだけ**で済むからです。

これが実務で最も価値のある複合インデックスのパターンです。

```
(絞り込みたい列, 並べたい列)
```

「あるユーザーの最新の注文10件」「ある商品の新着レビュー20件」——どれもこの形です。

実験が終わったら消します(第4章以降でクリーンな状態から始めるため)。

```sql
DROP INDEX idx_orders_uid_at ON orders;
```

## 3.6 バッファプール — メモリに乗るかどうかが全て

### 位置づけ

ここまで「ページを読む」と書いてきましたが、毎回ディスクを触っているわけではありません。InnoDB は読んだページを**バッファプール
**というメモリ領域にキャッシュします。

```sql
SELECT @@innodb_buffer_pool_size / 1024 / 1024 AS mb;
```

第1章で **128MB** に設定しました。そして作ったデータは合計200MB以上あります。**わざと全部乗らないようにしてあります。**

> 🔗 **Phase 2 との接続**: OS のページキャッシュと同じ発想ですが、InnoDB は**自前で**キャッシュを持ちます。DB
> は「どのページが今後使われそうか」を OS より正確に知っているからです(インデックスの上位ノードは絶対にまた使う、など)。

### ヒット率を測る

```sql
SHOW
GLOBAL STATUS WHERE Variable_name IN
  ('Innodb_buffer_pool_read_requests', 'Innodb_buffer_pool_reads');
```

- `read_requests` = ページを要求した回数(**論理読み**)
- `reads` = そのうち**ディスクから読んだ**回数(**物理読み**)

```
ヒット率 = (1 - reads / read_requests) × 100
```

**実務では 99% 以上が目標**です。95%を切っていたらメモリ不足を疑います。

### 実験: 冷えた状態と温まった状態

```sql
-- ① まず現在値を控える
SHOW
GLOBAL STATUS LIKE 'Innodb_buffer_pool_read%';

-- ② 全表走査を2回実行して時間を比較
SELECT SQL_NO_CACHE COUNT(*)
FROM orders
WHERE total_amount > 25000;
SELECT SQL_NO_CACHE COUNT(*)
FROM orders
WHERE total_amount > 25000;

-- ③ もう一度ステータスを見て、reads がどれだけ増えたか
SHOW
GLOBAL STATUS LIKE 'Innodb_buffer_pool_read%';
```

1回目は `reads` が大きく増え、2回目はほとんど増えません。**実行時間も2回目が明確に速い**はずです。これが「メモリに乗っている/いない」の差です。

> ⚠️ **再起動してもキャッシュは冷えません**
> MySQL 8 は既定で、**シャットダウン時にバッファプールの内容を保存し、起動時に復元します**(
`innodb_buffer_pool_dump_at_shutdown` / `load_at_startup`)
> 。本番の再起動直後に性能が落ちないための良い機能ですが、実験では邪魔です。本当に冷やしたいなら:
> ```sql
> SET GLOBAL innodb_buffer_pool_dump_at_shutdown = OFF;
> ```
> としてから `docker compose restart mysql` してください。

### LRU の工夫 — 全表走査からキャッシュを守る

バッファプールが満杯になったら、古いページを追い出します。基本は LRU(Least Recently Used)ですが、素朴な LRU には**致命的な弱点
**があります。

> **深夜バッチが巨大テーブルを全表走査すると、バッファプール全体がそのデータで埋め尽くされ、
> 本来キャッシュされているべき「よく使うページ」が全部追い出される。**
> 翌朝、アプリが軒並み遅い。

InnoDB はこれを防ぐため、LRU リストを2つに分けています。

```
[  young(新しい)  5/8  ][  old(古い)  3/8  ]
        ↑                        ↑
   よく使われるページ       新しく読んだページはここに入る
```

**新しく読んだページは、いきなり先頭には入りません。** 中間地点(old 側の先頭)に入り、**もう一度アクセスされて初めて** young
側に昇格します。

全表走査で読んだページは通常1回しか触られないので、**old 側にいるまま追い出されます**。よく使われるページは守られる、という設計です。

```sql
SELECT @@innodb_old_blocks_pct; -- 既定 37(%)
```

さらに詳しい状況は次で見られます。

```sql
SHOW
ENGINE INNODB STATUS
\G
```

`BUFFER POOL AND MEMORY` セクションに、`Buffer pool hit rate 1000 / 1000`、`Free buffers`、`Database pages`
などが出ています。この出力は第4章・第5章でも繰り返し使うので、場所を覚えておいてください。

### 書き込みはどうなるのか

ここまで読みの話でした。書き込みは、

1. バッファプール上のページを**メモリ上で書き換える**(ダーティページになる)
2. **ディスクへの反映は後回し**
3. 落ちても大丈夫なように、**ログだけ先に書く**

この3番目が **WAL(先行書き込みログ)**で、**第4章の主題**です。「なぜメモリを書き換えただけで『コミット完了』と言えるのか」という問いに、次章で答えます。

> 📖 **B+木の弱点と、LSM木への布石**
> B+木は「読みに最適化された」構造です。決められた位置に書く必要があるので、**書き込みはランダムI/Oになりがち**です。
> そこで、書き込みを常に追記にして後からまとめる **LSM木** という別の構造があり、RocksDB / Cassandra / HBase などが採用しています。
**書き込みが極端に多いシステム向け**の選択肢で、第7章の NoSQL で扱います。

## 3.7 インデックス設計の実務

### 張る候補の見つけ方

インデックスが効くのは、SQL の中の次の場所に現れる列です。

1. **`WHERE`** の絞り込み条件
2. **`JOIN`** の結合条件(第2章の駆動表の話)
3. **`ORDER BY` / `GROUP BY`**

そのうえで、**カーディナリティ(値の種類の多さ)が高い列**ほど効きます。

```sql
SELECT COUNT(DISTINCT user_id) AS uid, COUNT(DISTINCT status) AS st, COUNT(*) AS total
FROM orders;
```

`user_id` は約10万種類(50万行中)なので1値あたり5行に絞れます。一方 `status` は4種類しかないので、1値あたり12.5万行。*
*`status` 単独のインデックスはほぼ無意味**です。

ただし `status` も、複合インデックスの一部としてなら価値があります(`(user_id, status)` など)。**
「単独では無意味だが組み合わせると効く」**は普通に起きるので、単純に切り捨てないでください。

### 張りすぎの代償(再確認)

第1章の演習3でやった話です。インデックス1本につき:

- **B+木がもう1本増える** → ディスクとバッファプールを消費
- **INSERT / UPDATE / DELETE のたびに更新が必要** → インデックス10本なら、1行の追加で11本の木を更新
- **バッファプールの奪い合い** → データ用のキャッシュが減る

だから **「あったら便利かも」で張らない**。実際に遅いクエリがあり、`EXPLAIN` で改善が確認できてから張ります。

### 無駄なインデックスを見つける

MySQL には `sys` スキーマという便利なビュー群があります。

```sql
-- 冗長なインデックス(他のインデックスの一部で代替できるもの)
SELECT *
FROM sys.schema_redundant_indexes;

-- 一度も使われていないインデックス
SELECT *
FROM sys.schema_unused_indexes;
```

`(user_id)` と `(user_id, ordered_at)` の両方があれば、前者は後者の左端で代替できるので冗長です(**外部キー制約に使われている場合は消せません
** — 前回の質問の話です)。

`schema_unused_indexes` は、**MySQL 起動以降の統計**である点に注意してください。月次バッチでしか使わないインデックスが「未使用」と出ることがあります。判断は数週間観察してからです。

### 設計の手順(まとめ)

```
1. 遅いクエリを特定する(スロークエリログ)
2. EXPLAIN で type と Extra を見る
3. WHERE / JOIN / ORDER BY に出る列を洗い出す
4. 列順を決める:等値 → 範囲 → ソート
5. 可能なら SELECT する列も足してカバリングにできないか検討
6. 張って、EXPLAIN で type と key_len を確認
7. 実測して、本当に速くなったか確かめる
8. 既存インデックスと冗長になっていないか確認(統合できないか)
```

## 演習

### 演習1 — 段数を計算する

1行あたり 200バイトのテーブルがあり、主キーは `BIGINT` です。

(a) 葉ページ1枚に何行入るか
(b) 1億行を格納するには何段必要か
(c) このテーブルの主キー検索は、最悪何回のディスクI/Oで済むか

<details>
<summary>解答</summary>

**(a)** 使える領域を 15,200バイトとして、`15,200 ÷ 200 ≒ 76行`

**(b)** 内部ノードの扇出は約1,000(キー8 + ポインタ6 = 14バイト、`15,200 ÷ 14 ≒ 1,085`)。

| 段数 | 葉ページ数     | 行数     |
|----|-----------|--------|
| 2  | 1,000     | 76,000 |
| 3  | 1,000,000 | 7,600万 |
| 4  | 10億       | 7,600億 |

1億行は3段では足りず、**4段**必要です。

**(c) 最悪4回。ただし実際にはほぼ1回。**

根と内部ノードは全アクセスで共有されるので、バッファプールにほぼ確実に常駐します。根が1ページ、2段目が1,000ページ(16MB)
、3段目が100万ページ(16GB)…なので、3段目まで全部乗せるのは無理でも、**上位2段は必ず乗ります**。結局ディスクを触るのは下の1〜2回です。

**ここから得られる感覚**: データが100倍になっても、段数は1つ増えるだけ。**インデックスがある限り、テーブルの巨大化は検索速度をほとんど悪化させません
**。逆に言えば、遅いのは「インデックスが無いか、効いていない」からです。
</details>

### 演習2 — 二度引きを消す

次のクエリを `EXPLAIN` し、`Extra` に `Using index` を出すインデックスを設計してください。

```sql
SELECT user_id, COUNT(*), SUM(total_amount)
FROM orders
WHERE status = 'paid'
GROUP BY user_id;
```

<details>
<summary>解答</summary>

必要な列は `status`(絞り込み)、`user_id`(グループ化)、`total_amount`(集計)の3つ。全部インデックスに入れればカバリングになります。

```sql
CREATE INDEX idx_orders_covering ON orders (status, user_id, total_amount);
EXPLAIN
SELECT user_id, COUNT(*), SUM(total_amount)
FROM orders
WHERE status = 'paid'
GROUP BY user_id;
```

`Extra` に `Using index` が出ます。さらに、`status` で絞った中が `user_id` 順に並んでいるので、**`Using temporary`(GROUP BY
用の一時テーブル)も消えます**。

**列順が重要です。**

- `(status, user_id, total_amount)` ✅ 等値 → グループ化 → 集計値
- `(user_id, status, total_amount)` △ `status` の等値条件を先頭で使えない
- `(total_amount, status, user_id)` ❌ 左端が集計値では絞り込めない

**代償の確認**: このインデックスは `status`(1)+ `user_id`(8)+ `total_amount`(4)+ 主キー(8)
で1エントリ約20バイト+、50万行で十数MB。128MBのバッファプールに対して無視できない大きさです。*
*本当に頻繁に実行されるクエリでなければ張るべきではありません。**

終わったら `DROP INDEX idx_orders_covering ON orders;` で消してください。
</details>

### 演習3 — 列順を考える

次のクエリ群を1本のインデックスでできるだけ広くカバーしたい。列順を決めて、理由を述べてください。

```sql
-- A
SELECT *
FROM orders
WHERE user_id = ?
ORDER BY ordered_at DESC LIMIT 20;
-- B
SELECT *
FROM orders
WHERE user_id = ?
  AND status = 'paid';
-- C
SELECT *
FROM orders
WHERE user_id = ?
  AND ordered_at > ?;
```

<details>
<summary>解答例</summary>

**推奨: `(user_id, status, ordered_at)`**

理由を1つずつ。

- 3つとも `user_id` の等値条件を持つので、**左端は `user_id` で確定**
- `status` は**等値**、`ordered_at` は**範囲/ソート**。原則「等値 → 範囲」なので `status` が先
- A: `user_id` で絞った後、`status` を飛ばして `ordered_at` のソートに使えるか? → **使えません**。中間の列を飛ばすとソートには利用できず、
  `Using filesort` が残ります

つまり **A を優先するなら `(user_id, ordered_at)`、B を優先するなら `(user_id, status, ordered_at)`** となり、*
*1本で全部を最適にはできません**。

**実務での判断**:

1. **実行頻度と実行時間で優先順位をつける**。A(ユーザーの注文一覧)が画面表示で毎秒走るなら A 優先
2. `user_id` で既に5行程度に絞れるなら、**そもそも残りは誤差**。この規模なら `(user_id, ordered_at)` 1本で十分
3. 1ユーザーが数万件持つようなデータなら、2本張ることも検討する

**「1本で全部カバーしようとしない」**のが現実的な答えです。まず `user_id` で何行に絞れるかを測り、それで足りるなら追加しない。これが
3.7 の手順7「実測して確かめる」の意味です。
</details>

### 演習4 — 主キー設計

新しいテーブルの主キーとして、次の3案を比較してください。テーブルには 5,000万行が入り、セカンダリインデックスが3本ある想定です。

1. `BIGINT AUTO_INCREMENT`
2. `CHAR(36)` の UUID v4
3. `BINARY(16)` の UUID v7

<details>
<summary>解答</summary>

**容量への影響**(セカンダリ3本 × 5,000万行に主キーが埋め込まれる)

| 案 | 主キーサイズ | セカンダリへの追加分                  |
|---|--------|-----------------------------|
| 1 | 8バイト   | 8 × 5,000万 × 3 ≒ **1.2GB**  |
| 2 | 36バイト+ | 36 × 5,000万 × 3 ≒ **5.4GB** |
| 3 | 16バイト  | 16 × 5,000万 × 3 ≒ **2.4GB** |

案2は案1より **4GB以上多く**メモリとディスクを消費します。バッファプールへの影響は深刻です。

**挿入性能**

- 案1: 常に木の右端に追記。ページ分割なし。**最速**
- 案2: 挿入位置がランダム。**ページ分割が多発し、断片化して容量がさらに膨らむ**。ランダムI/Oも発生
- 案3: UUID v7 は先頭が時刻なので**ほぼ単調増加**。案1に近い挿入性能

**結論**

- 単一DBで完結し、IDが外部に露出しても構わない → **案1**
- IDを外部に晒すのでランダム性が欲しい、あるいは将来シャーディングする → **案3**
- 案2は避ける。どうしても UUID v4 が必要でも `BINARY(16)` にする

**補足の視点**: 「連番だと件数が推測される」というセキュリティ上の懸念には、**内部の主キーは案1のままにして、外部公開用の列を別に持つ
**という手もあります。主キー設計と外部公開IDを分けて考えるのが実務的です。
</details>

### 演習5 — 少し難しい

第2章 2.6④で「ヒットしすぎるとインデックスが使われない」ことを見ました。実際に境界を探してください。

```sql
CREATE INDEX idx_orders_amount ON orders (total_amount);

EXPLAIN
SELECT *
FROM orders
WHERE total_amount > 50000; -- ほぼ0件
EXPLAIN
SELECT *
FROM orders
WHERE total_amount > 40000;
EXPLAIN
SELECT *
FROM orders
WHERE total_amount > 20000;
EXPLAIN
SELECT *
FROM orders
WHERE total_amount > 1000; -- ほぼ全件
```

(a) `type` が `range` から `ALL` に変わる境界はどこか
(b) `SELECT *` を `SELECT total_amount` に変えると境界はどう動くか。なぜか

<details>
<summary>解答</summary>

**(a)** 環境によりますが、**全体の2〜3割程度**がヒットするあたりで `ALL` に切り替わります。第1章の生成では `total_amount` が
500〜50,500 の一様分布なので、閾値 35,000〜37,000 付近が境目になるはずです。

**(b) 境界が大きく動き、ほとんどの範囲で `range`(かつ `Using index`)のままになります。**

理由が本章の核心です。`SELECT total_amount` はインデックスだけで完結する(**カバリング**)ので、**二度引きが発生しません**
。全表走査が有利になる理由は「行数分のランダムアクセスが発生するから」でしたが、それが消えるのです。

結果、インデックスを順に舐めるだけで済み、しかもインデックスは行本体より小さいので**読むページ数も少ない**
。全表走査に負ける理由がありません。

**得られる教訓**: 「インデックスが効くかどうか」は、`WHERE` 句だけでは決まりません。**`SELECT` する列によって最適な計画が変わります
**。3.4 で「`SELECT *` を書くな」と言ったのは、まさにこの効果のためです。

終わったら `DROP INDEX idx_orders_amount ON orders;` で消してください。
</details>

## 次章の予告 — 第4章 トランザクションと ACID

第2章で診断、第3章で処方をやり、**読み取り性能の話はここで一区切り**です。第4章からは**書き込み**の世界に入ります。

3.6 の最後で、こう書きました。

> 書き込みはバッファプール上のページを**メモリで書き換えるだけ**。ディスクへの反映は後回し。落ちても大丈夫なようにログだけ先に書く。

**なぜそれで安全と言えるのか。** これが次章の問いです。

- **ACID** を1つずつ分解する。特に原子性と耐久性は**どう実装されているのか**
- **redo ログ(WAL)** — 「ログだけ先に書く」という発明
- `fsync` のコストと `innodb_flush_log_at_trx_commit`(**速さと確実さのトレードオフ**)
- **undo ログ** — ロールバックを可能にする仕組み(第5章の MVCC の土台にもなる)
- チェックポイント、doublewrite buffer、クラッシュリカバリ
- **実測**: 1件ずつコミット vs バッチコミットで、なぜ桁が変わるのか
- **実測**: トランザクション中に `docker kill` して、本当にロールバックされるか確かめる
