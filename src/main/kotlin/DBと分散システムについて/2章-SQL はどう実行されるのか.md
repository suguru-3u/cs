## この章で分かること

1. SQL は「何が欲しいか」しか書いていない。**「どう取るか」を決めるのは MySQL 側**である、という構造

3. `EXPLAIN ANALYZE` で**見積りと実測のズレ**を見る
4. オプティマイザの判断材料 = **コストと統計情報**。統計が古いと計画を間違える

6. インデックスが**あるのに効かない**典型パターン(実測で6つ)

## 2.1 SQL は「何が欲しいか」しか書いていない

### まずたとえ話から

タクシーに乗って「**東京駅までお願いします**」と言うとします。あなたは道順を指示していません。首都高を使うか、下道で行くか、どの交差点を曲がるかは運転手が決めます。運転手は「いまの時間帯なら首都高は渋滞している」といった**知識**を使って経路を選びます。

SQL はこれと同じです。

```sql
SELECT * FROM orders WHERE user_id = 42;
```

このSQLが言っているのは「**user_id が 42 の注文が欲しい**」だけです。「orders テーブルを頭から全部読んで、user_id を1つずつ比べろ」とは書いていません。どう取るかは MySQL が決めます。これを**宣言的**と言います。

対して、第1章で書いた Kotlin の CSV 検索は**手続き的**でした。「ファイルを開いて、1行ずつ読んで、前方一致を調べて…」と手順を全部書きましたね。速くしたければ自分でコードを書き直すしかありませんでした。

**SQL では、手順を決めるのは MySQL です。** だから同じ SQL でも、状況が変われば実行のされ方が変わります。

そしてここが実務で効いてくるポイントです。

> **SQL を読んでも、速いか遅いかは分からない。**
> **速いか遅いかを決めるのは実行計画であって、SQL そのものではない。**

だから `EXPLAIN` が要ります。

### 「どう取るか」には複数の選択肢がある

さっきの `WHERE user_id = 42` に対して、MySQL が取りうる方法は少なくとも2つあります。

| 方法 | 内容 | 読む行数 |
|---|---|---|
| A. 全表走査 | orders を先頭から全部読み、user_id を比べる | 500,000 |
| B. インデックス走査 | `idx_orders_user_id` を引いて、該当する行だけ取りに行く | 5前後 |

第1章で `idx_orders_user_id` を張ってあるので、MySQL は B を選びます。**選択肢を並べて、一番安そうなものを選ぶ**——これが**コストベース最適化**です。

### MySQL の中を通る道のり

第1章の全体図の②③④を細かくすると、こうなっています。

```
  SQL文字列
     │
     ▼
  ① パーサ            文法チェック、構文木にする
     │
     ▼
  ② 前処理・書き換え   ビュー展開、サブクエリの変形、
     │                 不要な条件の削除、定数の畳み込み
     ▼
  ③ オプティマイザ     統計情報を見ながら候補を評価し、
     │                 一番コストの低い実行計画を選ぶ    ← EXPLAIN が見せてくれるのはココ
     ▼
  ④ エグゼキュータ     計画に従って InnoDB に「この行をくれ」と要求
     │
     ▼
  ⑤ InnoDB            バッファプール / B+木から実際に読む   ← 第3章
```

②の書き換えは意外と強力で、書いた SQL がそのまま実行されるとは限りません。実際に見てみましょう。

```sql
EXPLAIN SELECT * FROM orders WHERE user_id = 40 + 2;
SHOW WARNINGS\G
```

```
Level: Note
 Code: 1003
Message: /* select#1 */ select `cs_study`.`orders`.`id` AS `id`, ...
         from `cs_study`.`orders` where (`cs_study`.`orders`.`user_id` = 42)
```

`40 + 2` が **`42` に畳み込まれています**。`EXPLAIN` の直後に `SHOW WARNINGS` を打つと、**MySQL が実際に実行しようとしている形**が見えます。サブクエリが JOIN に書き換わっていたりするので、「なぜこんな計画になるのか分からない」ときの調査に使えます。

## 2.2 EXPLAIN を読む

いよいよ本題です。第1章で作ったデータで手を動かします。

```bash
docker compose exec mysql mysql -uroot -prootpass cs_study
```

### 基本の形

```sql
EXPLAIN SELECT * FROM orders WHERE user_id = 42;
```

```
+----+-------------+--------+------------+------+--------------------+--------------------+---------+-------+------+----------+-------+
| id | select_type | table  | partitions | type | possible_keys      | key                | key_len | ref   | rows | filtered | Extra |
+----+-------------+--------+------------+------+--------------------+--------------------+---------+-------+------+----------+-------+
|  1 | SIMPLE      | orders | NULL       | ref  | idx_orders_user_id | idx_orders_user_id | 8       | const |    5 |   100.00 | NULL  |
+----+-------------+--------+------------+------+--------------------+--------------------+---------+-------+------+----------+-------+
```

> ※ 出力例です。`rows` の値などは環境で変わります。**自分の出力を見ながら読み進めてください。**

12列ありますが、**実務で毎回見るのは4つだけ**です。まずそこを押さえます。

### 最重要の4列

#### ① `type` — アクセス方法。**ここが8割**

その表からどうやって行を取るか。**良い順**に並べます。

| type | 意味 | 速さ |
|---|---|---|
| `system` / `const` | 主キーかユニークキーで1行に確定 | 最速 |
| `eq_ref` | JOIN で、相手1行につきこちら1行(主キー/ユニーク) | 非常に速い |
| `ref` | 非ユニークなインデックスで等値検索。**複数行ヒットしうる** | 速い |
| `range` | インデックスの範囲検索(`>` `<` `BETWEEN` `IN`) | まあ速い |
| `index` | **インデックス全体**を頭から舐める | **遅い**(全件相当) |
| `ALL` | **テーブル全体**を頭から舐める(全表走査) | **最も遅い** |

覚え方は、**`index` と `ALL` を見たら警戒**、これだけで十分です。

⚠️ 引っかかりやすいのが **`index`** です。名前から「インデックスが効いている」と読んでしまいますが、逆です。**インデックス全体を全部読む**という意味で、行数はテーブル全件と同じです。「インデックスを使った検索」は `ref` や `range` の方です。

ただし `type = ALL` が常に悪いわけではありません。**小さいテーブル(数百行)なら全表走査の方が速い**ので、MySQL はわざとそちらを選びます。インデックスを引いてから本体を取りに行く二度手間より、まとめて読んだ方が安いからです。**「`ALL` = 即バグ」ではなく、「大きいテーブルの `ALL` を疑う」**が正しい構えです。

#### ② `key` — 実際に使ったインデックス

`possible_keys`(使えたかもしれない候補)と `key`(実際に選んだもの)の2つがあります。実務で刺さるのは次の状況です。

- `possible_keys` が `NULL` → **そもそも候補がない**。インデックスを張るべきか、書き方が悪い(2.6)
- `possible_keys` に名前があるのに `key` が `NULL` → **候補はあったが、使わない方が安いと判断された**。統計がおかしいか、条件がヒットしすぎている

この2つは対処がまったく違うので、区別してください。

#### ③ `rows` — 読むと**見積もった**行数

**推定値です。実測値ではありません。** インデックスの統計情報から「だいたいこれくらいの行に触るだろう」と計算した数字です。

だから **`rows` が実際と大きくズレていたら、統計情報を疑う**、という使い方をします(2.4)。

#### ④ `Extra` — 補足。ここに地雷が埋まっている

頻出のものだけ挙げます。

| 表示 | 意味 | 良い/悪い |
|---|---|---|
| `Using index` | **カバリングインデックス**。インデックスだけで完結し、テーブル本体を読んでいない | 🎉 とても良い |
| `Using where` | 行を取ってから条件で絞った | 普通 |
| `Using index condition` | インデックス条件プッシュダウン(ICP)。InnoDB 側で絞った | 良い |
| `Using filesort` | **ソートを別途やった**。メモリまたはディスク上で | ⚠️ 大きいと重い |
| `Using temporary` | **一時テーブルを作った**。GROUP BY / DISTINCT で起きやすい | ⚠️ 重い |
| `Using join buffer (hash join)` | ハッシュ結合を使った | 状況次第 |

`Using index`(良い)と `Using index condition`(良い)と `Using where`(普通)は名前が紛らわしいので、**`Using index` = 本体を読んでいない、が最高**とだけ覚えてください。

> 💡 `Using filesort` は「ファイルにソートした」という意味ではありません。**メモリ上で完結することも多い**です。名前が悪いだけなので、見ただけで慌てないでください。ただし大量行のソートは重いので、`rows` と併せて見ます。

### 残りの列(軽く)

| 列 | 意味 |
|---|---|
| `id` | クエリブロックの番号。サブクエリや UNION があると増える。**大きい id ほど先に実行** |
| `select_type` | `SIMPLE`(単純)/ `PRIMARY` / `SUBQUERY` / `DERIVED`(FROM句のサブクエリ)など |
| `partitions` | パーティションを使っていれば表示(第7章) |
| `key_len` | **使ったインデックスの何バイト目まで使ったか**。複合インデックスで超重要(第3章) |
| `ref` | インデックスと比較された相手(`const` = 定数、または列名) |
| `filtered` | `rows` のうち、条件を通過して**次に渡る行の割合(%)** |

`rows × filtered / 100` が「次のステップに渡る行数」です。JOIN のとき、この数字が次のテーブルを引く回数になるので効いてきます。

### 手を動かす: 4パターン比べる

```sql
-- (a) 主キー
EXPLAIN SELECT * FROM products WHERE id = 999999;

-- (b) インデックスなしの列
EXPLAIN SELECT * FROM products WHERE name = 'item999999';

-- (c) 非ユニークなインデックス
EXPLAIN SELECT * FROM orders WHERE user_id = 42;

-- (d) インデックスなしの範囲検索
EXPLAIN SELECT * FROM orders WHERE ordered_at > NOW() - INTERVAL 7 DAY;
```

**期待される `type`**:

| | type | key | rows | 解釈 |
|---|---|---|---|---|
| (a) | `const` | PRIMARY | 1 | 1行に確定 |
| (b) | `ALL` | NULL | ~100万 | 全表走査 |
| (c) | `ref` | idx_orders_user_id | 数件 | インデックスで絞れた |
| (d) | `ALL` | NULL | ~50万 | **範囲検索だがインデックスがない** |

(d)は「直近7日の注文」という、実務で毎日書くクエリです。第1章で `ordered_at` にわざとインデックスを張らなかったので、いまは全表走査になります。あとで直します。

## 2.3 EXPLAIN ANALYZE — 見積りと実測を比べる

`EXPLAIN` は「MySQL がこうするつもりだ」という**予定**です。予定と実際がズレることがあるので、実測できる道具があります。

```sql
EXPLAIN ANALYZE SELECT * FROM orders WHERE ordered_at > NOW() - INTERVAL 7 DAY\G
```

> ⚠️ **`EXPLAIN ANALYZE` はクエリを実際に実行します。** 10秒かかるクエリは10秒かかります。本番で重いクエリに使うときは要注意です(`SELECT` が対象で、更新系には使えません)。

出力は木構造(`FORMAT=TREE` と同じ形)になります。

```
-> Filter: (orders.ordered_at > <cache>((now() - interval 7 day)))
     (cost=51000 rows=166000) (actual time=0.15..380 rows=9612 loops=1)
    -> Table scan on orders
     (cost=51000 rows=498000) (actual time=0.10..300 rows=500000 loops=1)
```

**読み方は「内側(下)から外側(上)へ」**です。プログラムの呼び出しと逆で、下の行が先に実行されます。

- 一番下: `Table scan on orders` — 全表走査で **50万行**読んだ
- その上: `Filter` — 条件で絞って **9,612行**残った

各行のカッコの意味:

| 表記 | 意味 |
|---|---|
| `cost=51000` | オプティマイザが見積もったコスト(単位は「1行読む≒1」の相対値) |
| `rows=498000` | **見積もり**行数 |
| `actual time=0.10..300` | **実測**。`最初の1行が出るまで..全部出し終わるまで` のミリ秒 |
| `rows=9612` | **実測**の行数 |
| `loops=1` | このステップが実行された回数(JOIN の内側だと増える) |

### ここが実務での使いどころ

**見積り `rows` と実測 `rows` を比べます。**

```
(cost=51000 rows=166000) (actual ... rows=9612 loops=1)
             ^^^^^^^^^^^             ^^^^^^^^
             見積り 16.6万            実測 9,612
```

**17倍もズレています。** オプティマイザは「16万行くらい返るだろう」と思って計画を立てたのに、実際は1万行以下でした。

この「ズレ」が、**間違った実行計画が選ばれる原因**です。16万行返ると思えば「どうせ大量に返るなら全表走査の方が安い」と判断しますが、本当は1万行なら、インデックスを引いた方がずっと速かったかもしれません。

> 📌 **調査の型として覚えてください**
> 1. クエリが遅い → `EXPLAIN` で `type` を見る
> 2. `type` が妥当なのに遅い → `EXPLAIN ANALYZE` で見積りと実測を比べる
> 3. 大きくズレている → **統計情報を疑う**(次節)

### `actual time` の 2つの数字

`actual time=0.10..300` の左右には意味があります。

- 左(0.10ms) = **最初の1行**が出るまで
- 右(300ms) = **最後の1行**が出るまで

`LIMIT 10` を付けたクエリなら、左の数字が小さければ体感は速いです。逆に、ソートや集計は「全部読み終わらないと1行目が出せない」ので、**左右がほぼ同じ値**になります。ここを見ると「途中で止められるクエリか、全部読まないと終わらないクエリか」が分かります。

## 2.4 オプティマイザは何を根拠に決めているのか

### コスト = 触る行数 × 単価

MySQL は候補ごとにコストを計算し、一番安いものを選びます。おおまかには、

```
コスト ≒ (読むページ数 × ディスク読み込みの単価)
       + (評価する行数 × CPU の単価)
```

単価はテーブルに保存されていて、覗くことができます。

```sql
SELECT * FROM mysql.server_cost;
SELECT * FROM mysql.engine_cost;
```

`row_evaluate_cost`(1行を評価するコスト)や `io_block_read_cost`(1ページ読むコスト)といった値が入っています。通常は触りませんが、**「行数 × 単価で計算している」という事実**が分かれば十分です。

つまり、**コスト計算の精度は「行数の見積り精度」でほぼ決まります**。そして行数の見積りに使うのが統計情報です。

### 統計情報の実体

```sql
SELECT index_name, stat_name, stat_value, stat_description
FROM mysql.innodb_index_stats
WHERE database_name = 'cs_study' AND table_name = 'orders';
```

```
+--------------------+--------------+------------+-----------------------------------+
| index_name         | stat_name    | stat_value | stat_description                  |
+--------------------+--------------+------------+-----------------------------------+
| PRIMARY            | n_diff_pfx01 |     498000 | id                                |
| PRIMARY            | n_leaf_pages |       1580 | Number of leaf pages in the index  |
| PRIMARY            | size         |       1620 | Number of pages in the index       |
| idx_orders_user_id | n_diff_pfx01 |      99500 | user_id                           |
| ...                                                                                 |
+--------------------+--------------+------------+-----------------------------------+
```

`n_diff_pfx01` が **カーディナリティ**(その列の異なる値の個数)です。`idx_orders_user_id` は約99,500種類。テーブルは50万行なので、

```
1つの user_id あたりの行数 ≒ 500,000 / 99,500 ≒ 5行
```

だから `EXPLAIN` の `rows` が 5 だったわけです。**推定の正体はこの割り算**です。

⚠️ そして重要なのが、**この統計はサンプリングで作られている**ことです(既定では各インデックスから20ページ程度)。全行を数えているわけではないので、**データが偏っていると外れます**。

### 統計が古くなるとどうなるか

```sql
SELECT @@innodb_stats_persistent,      -- 統計をディスクに保存するか(既定 ON)
       @@innodb_stats_auto_recalc,     -- 自動再計算するか(既定 ON)
       @@innodb_stats_persistent_sample_pages;  -- サンプル数(既定 20)
```

自動再計算は **テーブルの約10%の行が変更されたとき**に走ります。裏を返すと、

- **10%未満の変更が積み重なっている間は、統計は更新されない**
- 大量 INSERT の直後は、統計が追いついていないことがある

これが「**昨日まで速かったクエリが今日から遅い**」の代表的な原因です。手動で更新できます。

```sql
ANALYZE TABLE orders;
```

数秒で終わります(テーブルをロックしません)。**遅くなったクエリの調査で、まず試す価値がある操作**です。

### ヒストグラム — 偏りに対処する

カーディナリティだけでは「値の偏り」を表現できません。例えば `orders.status` は4種類ですが、実際には `paid` が90%を占める、といったことが普通に起きます。カーディナリティ4だけ見ると、MySQL は「どの値も25%くらいだろう」と考えてしまいます。

そこで**ヒストグラム**を作れます。

```sql
ANALYZE TABLE orders UPDATE HISTOGRAM ON status WITH 16 BUCKETS;

SELECT histogram FROM information_schema.column_statistics
WHERE table_name = 'orders'\G
```

値ごとの実際の分布が JSON で保存され、オプティマイザが `WHERE status = 'canceled'` の見積り精度を上げられます。**インデックスのない列にも作れる**のが利点です。

不要になったら削除します。

```sql
ANALYZE TABLE orders DROP HISTOGRAM ON status;
```

### オプティマイザの思考を覗く(おまけ)

「なぜこの計画を選んだのか」を全部見ることもできます。

```sql
SET optimizer_trace = 'enabled=on';
SELECT * FROM orders WHERE user_id = 42;
SELECT * FROM information_schema.optimizer_trace\G
SET optimizer_trace = 'enabled=off';
```

各候補のコスト計算過程が JSON で出てきます。**長大なので普段は使いません**が、「どうしてもインデックスを使ってくれない」ときの最終手段として、存在だけ知っておいてください。

## 2.5 JOIN はどう実行されるのか

### 基本は Nested Loop(入れ子ループ)

```sql
SELECT o.id, u.name
FROM orders o
JOIN users u ON o.user_id = u.id
WHERE u.name = 'user42';
```

MySQL の基本戦略は、Kotlin で書くとこうです。

```kotlin
for (u in users.filter { it.name == "user42" }) {   // 駆動表(先に読む方)
    for (o in orders.where { it.userId == u.id }) { // 内側は毎回引く
        emit(o.id, u.name)
    }
}
```

**外側のループを「駆動表(driving table)」と呼びます。** そして、

> **JOIN の性能は、どちらを駆動表にするかでほぼ決まります。**

なぜか。内側のループは**外側の行数だけ繰り返される**からです。外側が1行なら内側を1回引くだけですが、外側が50万行なら内側を50万回引きます。

だからオプティマイザは「**絞り込んだ結果が少ない方を外側に置く**」よう試みます。上の例なら `u.name = 'user42'` で1行に絞れるので、`users` が駆動表になるべきです。

`EXPLAIN` の**上から順が、そのまま JOIN の順序**です。

```sql
EXPLAIN SELECT o.id, u.name FROM orders o JOIN users u ON o.user_id = u.id
WHERE u.name = 'user42';
```

```
| id | table | type | key                | rows   | Extra       |
|  1 | u     | ALL  | NULL               | 99000  | Using where |   ← 駆動表(先)
|  1 | o     | ref  | idx_orders_user_id | 5      | NULL        |   ← 内側(後)
```

`users.name` にインデックスがないので `u` 自体は全表走査ですが、**駆動表の選択としては正しい**です。1行に絞ってから `orders` を5行引いています。

### 順序をわざと逆にして測る

`STRAIGHT_JOIN` を使うと、**書いた順に強制**できます。悪い計画を体験してみましょう。

```sql
-- 良い計画(MySQL の判断に任せる)
SELECT SQL_NO_CACHE COUNT(*)
FROM orders o JOIN users u ON o.user_id = u.id
WHERE u.name = 'user42';

-- 悪い計画(orders を駆動表に強制)
SELECT SQL_NO_CACHE COUNT(*)
FROM orders o STRAIGHT_JOIN users u ON o.user_id = u.id
WHERE u.name = 'user42';
```

後者は「50万件の注文を1件ずつ読んで、そのたびに users を主キーで引く」ことになります。**実行時間を比べて記録してください。** 桁が変わるはずです。

> 💼 **実務での意味**: 「サブクエリを JOIN に書き換えたら速くなった/遅くなった」という現象の正体は、たいてい**駆動表が変わったこと**です。SQL の見た目ではなく、`EXPLAIN` の**行の順序**を見れば説明がつきます。

### Hash Join(MySQL 8.0.18 以降)

内側にインデックスがない JOIN は、Nested Loop だと悲惨です(毎回全表走査するので)。そこで MySQL 8 は**ハッシュ結合**を使います。

```kotlin
// 1. 小さい方をメモリ上のハッシュマップにする(ビルド)
val hash = users.associateBy { it.id }
// 2. 大きい方を1回だけ舐めて、ハッシュを引く(プローブ)
for (o in orders) {
    hash[o.userId]?.let { emit(o.id, it.name) }
}
```

**それぞれのテーブルを1回ずつしか読みません。** 大量データ同士の結合ではこちらが圧倒的に有利です。

```sql
EXPLAIN FORMAT=TREE
SELECT COUNT(*) FROM orders o JOIN users u ON o.total_amount = u.id\G
```

```
-> Inner hash join (o.total_amount = u.id)  (cost=...)
    -> Table scan on o  (rows=498000)
    -> Hash
        -> Table scan on u  (rows=99000)
```

`Inner hash join` と `Hash` が出ていれば成立しています。使えるメモリは `join_buffer_size` で決まり、溢れるとディスクに書きます(遅くなる)。

> 📖 **歴史メモ**: MySQL 8.0.20 より前は `Block Nested Loop` という中間的な方式がありましたが、**現在は削除されて Hash Join に置き換わっています**。古い記事で「BNL」を見かけたら、8.0.20 以降には存在しないものだと思ってください。

### オプティマイザヒント

どうしても計画を固定したいときは、ヒントを書けます。

```sql
SELECT /*+ INDEX(orders idx_orders_user_id) */ ...      -- このインデックスを使え
SELECT /*+ NO_INDEX(orders idx_orders_user_id) */ ...   -- 使うな
SELECT /*+ JOIN_ORDER(u, o) */ ...                      -- この順で結合しろ
```

ただし**最後の手段**です。ヒントは「今のデータ分布での正解」を固定するので、データが増えると逆に足かせになります。まず統計を疑い、SQL を見直し、それでもダメならヒント、の順です。

## 2.6 インデックスが「あるのに効かない」6パターン

ここが実務のバグ密集地帯です。**全部実際に `EXPLAIN` して、`type` が何になるか確かめてください。**

準備として、`ordered_at` にインデックスを張ります(この章の間だけ使います)。

```sql
CREATE INDEX idx_orders_ordered_at ON orders (ordered_at);
```

### ① 列に関数・演算を適用する

```sql
-- ❌ 効かない
EXPLAIN SELECT * FROM orders WHERE DATE(ordered_at) = '2026-08-01';
-- ✅ 効く
EXPLAIN SELECT * FROM orders
WHERE ordered_at >= '2026-08-01' AND ordered_at < '2026-08-02';
```

インデックスは `ordered_at` の**生の値**を順に並べたものです。`DATE()` を通した値は並んでいないので、全行に関数を適用して確かめるしかありません。

**原則: `WHERE` の左辺に列を裸で置く。** 加工するなら右辺(定数側)でやります。

> 補足: MySQL 8 には**関数インデックス**(`CREATE INDEX ... ((DATE(ordered_at)))`)もあります。どうしても関数形が必要なら選択肢になりますが、まずは範囲条件への書き換えを検討してください。

### ② 暗黙の型変換 — 最も見つけにくい

```sql
-- users.email は VARCHAR(255)、ユニークインデックスあり
EXPLAIN SELECT * FROM users WHERE email = 'user42@example.com';  -- ✅ const
EXPLAIN SELECT * FROM users WHERE email = 12345;                 -- ❌ ALL !!
```

文字列の列を数値と比較すると、MySQL は**列側を数値に変換**して比べます。つまり全行に変換をかけるので、インデックスが使えません。

**実務では、これが一番怖いパターンです。** 理由は3つ。

1. **SQL は正しく動く**(結果は返る)ので、テストで気づかない
2. データが少ないうちは速いので、本番でデータが増えてから顕在化する
3. アプリのコードでは `Long` を渡しているつもりが、列は `VARCHAR` だった、というだけで起きる

第6章で MyBatis を扱うとき、**Kotlin の型と列の型が食い違っていないか**を確認するポイントとして戻ってきます。

### ③ 前方一致でない LIKE

```sql
EXPLAIN SELECT * FROM products WHERE name LIKE 'item999%';   -- ✅ range
EXPLAIN SELECT * FROM products WHERE name LIKE '%999999';    -- ❌ ALL
```

インデックスは辞書と同じで「前から順」に並んでいます。辞書で「〜で終わる単語」を引けないのと同じ理屈です。**中間一致・後方一致が必要なら、全文検索インデックスや専用の検索エンジン(Elasticsearch 等)の出番**です。

※ この実験には演習3で使った `idx_products_name` が必要です。無ければ一時的に作ってください。

### ④ ヒットしすぎる範囲条件

```sql
EXPLAIN SELECT * FROM orders WHERE ordered_at > '2020-01-01';
```

インデックスがあるのに `type = ALL` になることがあります。これは**バグではなく正しい判断**です。

インデックス経由で行を取ると、「インデックスを引く → 本体を取りに行く」という**ランダムアクセス**が行数分発生します。全体の3割も返るなら、**順番に全部読んだ方が速い**のです。第3章でこの構造を詳しくやります。

**教訓**: 「インデックスを張ったのに `ALL` のまま」を見たら、**まず返る行数の割合**を確認してください。

### ⑤ ソートでインデックスが使えていない

```sql
EXPLAIN SELECT * FROM orders ORDER BY total_amount DESC LIMIT 10;
```

`Extra` に **`Using filesort`** が出ます。`total_amount` にインデックスがないので、50万行を全部読んでソートし、上位10件だけ返しています。**10件欲しいだけなのに50万行読んでいる**わけです。

インデックスがあれば、「並んでいるものの先頭から10件取る」だけで済みます。これも第3章の主題です。

### ⑥ 深いページング(実務で頻出)

```sql
SELECT * FROM orders ORDER BY id LIMIT 10 OFFSET 0;       -- 速い
SELECT * FROM orders ORDER BY id LIMIT 10 OFFSET 400000;  -- 遅い
```

**両方 `EXPLAIN ANALYZE` して、実測時間を比べてください。**

`OFFSET 400000` は「400,000行読んで**捨ててから**、10行返す」という動作です。飛ばす仕組みはありません。だから**ページ番号が進むほど線形に遅くなります**。

対策は **シークメソッド(キーセットページネーション)** です。

```sql
-- ❌ ページ番号方式
SELECT * FROM orders ORDER BY id LIMIT 10 OFFSET 400000;
-- ✅ 「前ページの最後のid」から続ける
SELECT * FROM orders WHERE id > 400000 ORDER BY id LIMIT 10;
```

後者は何ページ目でも一定速度です。管理画面の一覧が「後ろのページだけタイムアウトする」という障害は、ほぼこれが原因です。

**この章の実験が終わったら、インデックスを消しておいてください**(第3章で「無い状態」から始めます)。

```sql
DROP INDEX idx_orders_ordered_at ON orders;
```

## 2.7 実務: 「昨日まで速かったのに」の調査手順

第9章で本格的にやりますが、この章の道具だけで組める手順を書いておきます。

```
1. 本当にそのクエリか?を確定する
   → スロークエリログ / SHOW PROCESSLIST で「いま重いSQL」を特定
   → 思い込みで別のクエリを調べるのが一番の時間ロス

2. EXPLAIN を取る
   → type が ALL / index になっていないか
   → key が NULL になっていないか
   → possible_keys はあるのに key が NULL なら「使わない判断をされた」

3. EXPLAIN ANALYZE で見積りと実測を比べる
   → rows のズレが大きい → 統計を疑う

4. ANALYZE TABLE を実行して、計画が変わるか見る
   → 変われば原因は統計。定期実行や、偏りがあればヒストグラムを検討

5. それでもダメなら SQL を書き換える(2.6 の6パターンを確認)

6. 最後の手段としてヒント、またはインデックス追加(第3章)
```

**「昨日まで速かった」の原因ランキング**(体感順):

1. **データ量が閾値を越えた** — 「返る行数の割合」が変わり、④のようにプランが切り替わった
2. **統計が古い/更新された** — どちらの向きでも起きる
3. **渡された値が変わった** — `WHERE status = ?` に `paid`(90%)が来るか `canceled`(1%)が来るかで最適な計画は違う。MySQL は実行のたびに最適化するので、**同じSQLでも値によって計画が変わる**
4. **誰かがインデックスを消した/追加した**
5. **バージョンアップでオプティマイザの挙動が変わった**

3番は特に覚えておいてください。「再現しない」「特定のユーザーだけ遅い」という報告の正体は、たいていこれです。

## 演習

### 演習1 — 計画を予測する

`EXPLAIN` を実行する**前に**、`type` が何になるか予想してから確かめてください。

```sql
-- (1)
SELECT * FROM orders WHERE id IN (1, 2, 3);
-- (2)
SELECT * FROM orders WHERE user_id = 42 AND status = 'paid';
-- (3)
SELECT COUNT(*) FROM orders;
-- (4)
SELECT * FROM order_items WHERE order_id = 100;
```

<details>
<summary>解答</summary>

**(1) `range`** — 主キーだが複数値なので `const` にはならず、範囲扱いになります(`IN` は `range`)。

**(2) `ref`** — `idx_orders_user_id` で `user_id = 42` の5行程度を取り、そこから `status` を `Using where` で絞ります。**`status` にはインデックスがないので、絞り込みは行を取った後**です。5行なら問題ありませんが、もし1ユーザーが10万件注文していたら `(user_id, status)` の複合インデックスが効きます(第3章)。

**(3) `index`** — `Extra` に `Using index`。カウントだけなら本体を読む必要がないので、**一番小さいインデックス**を全部舐めます。それでも全件舐めることに変わりはないので、巨大テーブルの `COUNT(*)` は重い、が結論です。

**(4) `ref`** — `idx_order_items_order_id` を使い、2行程度。

**振り返りのポイント**: (3)の `index` に「インデックスを使っているから速い」と思わなかったか、確認してください。
</details>

### 演習2 — 暗黙の型変換を検出する

`users.email` は `VARCHAR` です。次の2つを `EXPLAIN` し、なぜ差が出るか説明してください。そのうえで、**アプリのコードでこれを防ぐ方法**を考えてください。

```sql
SELECT * FROM users WHERE email = 'user42@example.com';
SELECT * FROM users WHERE email = 42;
```

<details>
<summary>解答</summary>

前者は `type = const`(ユニークインデックスで1行)。後者は `type = ALL` で全表走査になります。

**理由**: 文字列と数値の比較では、MySQL は**文字列側を数値に変換**します(比較のルールがそう定められています)。つまり `CAST(email AS DOUBLE) = 42` と同じことになり、①の「列に関数を適用した」のと同じ状態になります。インデックスは `email` の文字列としての順序で並んでいるので使えません。

`SHOW WARNINGS` を見ると型変換の警告が出ることもあります。

**アプリ側での防ぎ方**:

1. **DTO(data class)の型を列の型に厳密に合わせる**。`VARCHAR` の列は `String` で受ける
2. **ID 系の列の型を統一する**。「ユーザーIDは `BIGINT`」「商品コードは `VARCHAR`」と決めて、混ぜない
3. 特に危ないのが「**数字だけの文字列コード**」です。`product_code VARCHAR(20)` に `'0001234'` が入っている場合、Kotlin 側で `Int` にしてしまうと型変換が起きるうえ、**先頭のゼロも消えます**
4. レビュー観点として「WHERE 句の左右の型は一致しているか」を持つ

第6章で MyBatis のパラメータ型を扱うとき、ここに戻ってきます。
</details>

### 演習3 — 駆動表を体感する

2.5 の `STRAIGHT_JOIN` の実験を実行し、実行時間を記録してください。そのうえで、**なぜ何倍も違うのか**を「読む行数」の言葉で説明してください。

<details>
<summary>解答例</summary>

**良い計画(users が駆動表)**
1. `users` を全表走査(約10万行)して `name='user42'` の1行を得る
2. その1行について `idx_orders_user_id` を引き、5行取る
→ 触る行数 ≒ 10万 + 5

**悪い計画(orders が駆動表)**
1. `orders` を全表走査(50万行)
2. **50万行それぞれについて** `users` を主キーで1行引く
3. 引いた後に `name = 'user42'` で捨てる
→ 触る行数 ≒ 50万 + 50万回のインデックス参照 = 100万相当

**約10倍の差**です。しかも後者は50万回のランダムアクセスを含むので、実測ではさらに開くことが多いです。

**本質**: 内側のループは外側の行数だけ回るので、**「先に絞れる方を外に置く」**のが鉄則。オプティマイザはこれを自動でやってくれていますが、統計が狂うと間違えます。「JOIN が突然遅くなった」ときは、`EXPLAIN` の**行の順序が入れ替わっていないか**を真っ先に見てください。
</details>

### 演習4 — ページングを直す

```sql
SELECT * FROM orders ORDER BY id LIMIT 10 OFFSET 400000;
```

これを `EXPLAIN ANALYZE` で測り、シークメソッドに書き換えて再測定してください。そのうえで、**シークメソッドが使えないケース**を1つ挙げてください。

<details>
<summary>解答例</summary>

書き換え:

```sql
SELECT * FROM orders WHERE id > 400000 ORDER BY id LIMIT 10;
```

`OFFSET` 版は `actual time` が数百 ms、シーク版は 1ms 未満になるはずです。`EXPLAIN ANALYZE` の下段を見ると、`OFFSET` 版は `rows=400010` 読んでいるのに対し、シーク版は `rows=10` です。**捨てるために読んでいた**ことがはっきり見えます。

**シークメソッドが使えないケース**:

1. **「5ページ目に飛ぶ」ができない**。前ページの最後の値が必要なので、「次へ/前へ」のUIにしか使えません。ページ番号リンクが要件なら使えない
2. **ソート順が一意でない場合**。`ORDER BY ordered_at` のように重複しうる列だと、境界で行が飛んだり重複したりします。`ORDER BY ordered_at, id` のように**一意になるまでキーを足す**必要があります
3. 任意の列でソートを切り替えるUIだと、その列すべてにインデックスが要ります

**実務的な落としどころ**: 管理画面ならページ番号を諦めて「次へ」方式にする、あるいは「1000ページ以降は表示しない/検索条件を絞ってもらう」という仕様にすることが多いです。Google の検索結果も深いページには行けませんね。
</details>

### 演習5 — 少し難しい

`orders.status` は 4種類の値を持ちますが、実データでは偏りがあります(第1章の生成では概ね均等ですが、実務では `paid` が大半になります)。

次を考えてください。

(a) 現在のデータで `SELECT COUNT(*) FROM orders GROUP BY status;` を実行し、分布を確認する
(b) `status` にインデックスを張ったとして、`WHERE status = 'paid'` と `WHERE status = 'canceled'` で最適な実行計画は同じか
(c) MySQL が (b) を正しく判断するために必要なものは何か

<details>
<summary>解答</summary>

**(a)** 第1章の生成では `RAND()` で4値を均等に振っているので、各12.5万件前後になります。

**(b) 同じではありません。**

- `paid` が90%を占めるなら、インデックスを引いても結局45万行を取りに行くことになり、**全表走査の方が速い**
- `canceled` が1%(5000行)なら、**インデックスを引く方が圧倒的に速い**

**同じSQL・同じインデックスでも、値によって最適解が反転します。** これが 2.7 の原因ランキング3番の正体です。

**(c) 値ごとの分布情報、つまりヒストグラムです。**

カーディナリティ(=4)だけでは「各値25%」としか推定できず、`paid` でも `canceled` でも同じ計画になってしまいます。

```sql
ANALYZE TABLE orders UPDATE HISTOGRAM ON status WITH 16 BUCKETS;
```

これで値ごとの割合が保存され、値に応じて計画を切り替えられるようになります。

**発展的な視点**: ただし、これは「実行のたびに最適化する」MySQL だからできることです。実行計画をキャッシュして使い回す DB では、最初に来た値で作った計画が後の値に合わない、という別の問題(パラメータスニッフィング)が起きます。MySQL は毎回最適化するのでこの問題が起きにくい代わりに、**最適化のCPUコストを毎回払っています**。トレードオフです。
</details>
