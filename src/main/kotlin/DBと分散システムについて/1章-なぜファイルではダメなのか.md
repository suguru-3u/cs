## 1.1 まず、DBなしで在庫管理を作ってみる

いきなり「DBとは」から入ると退屈なので、逆から行きます。**DBを使わずに作って、壊れるところを見ます。**

題材はシンプルに、EC サイトの商品在庫です。要件はこれだけ。

- 商品を100万件保持する(id, 商品名, 価格, 在庫数)
- id を指定して1件取り出せる
- 「価格が5000円より高い商品の件数」を数えられる
- 注文が入ったら在庫を1減らす

素直に CSV でやってみましょう。

### 実験1: 検索が線形時間になる

```kotlin
// FileDbDemo1.kt
import java.io.File
import kotlin.system.measureTimeMillis

fun main() {
    val csv = File("products.csv")

    // (1) 100万行の「商品テーブル」をCSVで作る
    val genMs = measureTimeMillis {
        csv.bufferedWriter().use { w ->
            w.write("id,name,price,stock\n")
            for (i in 1..1_000_000) {
                w.write("$i,item$i,${(i % 9000) + 100},${i % 50}\n")
            }
        }
    }
    println("生成: ${genMs}ms / サイズ ${csv.length() / 1024 / 1024}MB")

    // (2) id = 999999 を1件だけ探す
    //     SQL なら SELECT * FROM products WHERE id = 999999
    repeat(2) {
        var found: String? = null
        val ms = measureTimeMillis {
            csv.bufferedReader().use { r ->
                while (true) {
                    val line = r.readLine() ?: break
                    if (line.startsWith("999999,")) {
                        found = line
                        break
                    }
                }
            }
        }
        println("1件検索: ${ms}ms -> $found")
    }

    // (3) 集計
    //     SQL なら SELECT COUNT(*) FROM products WHERE price > 5000
    var count = 0
    val aggMs = measureTimeMillis {
        csv.bufferedReader().use { r ->
            r.readLine() // ヘッダを捨てる
            while (true) {
                val line = r.readLine() ?: break
                if (line.split(",")[2].toInt() > 5000) count++
            }
        }
    }
    println("集計: ${aggMs}ms -> ${count}件")
}
```

**手元の実測値**(JVM 21 / Linux / SSD。皆さんの環境では数字が変わります。**自分の値をメモしてください**):

```
生成: 1246ms / サイズ 24MB
1件検索: 236ms -> 999999,item999999,1099,49
1件検索: 157ms -> 999999,item999999,1099,49        ← 2回目は速い(OSページキャッシュ)
集計: 422ms -> 454989件
```

2回目の検索が速くなっているのは、Phase 2 でやった **OSのページキャッシュ**が効いているからです。ディスクではなくメモリから読んでいます。

さて、**1件取り出すのに 157ms** です。これがどれくらい絶望的な数字か、実務の感覚に翻訳します。

- 1リクエストで商品を10件表示する画面 → 1.5秒(それだけで終わる)
- 秒間100リクエスト来る → CPU が完全に溶ける
- しかも**データが増えると比例して遅くなる**(O(n))。1000万件なら10倍

そして本質的な問題は、**この構造では絶対に速くできない**ことです。id が何であれ、ファイルを頭から順に読むしかない。「12番目の行が欲しい」と分かっていても、
**改行がどこにあるか分からないので飛べない**のです。

> 🔗 **Phase 2 との接続**: ファイルは「バイト列」であって「行の配列」ではありませんでした。ランダムアクセスするには「何バイト目」を知っている必要があります。この「どこにあるか」を管理する仕組みが、第3章でやる
**インデックス**の出発点です。

### 実験2: 同時に更新すると壊れる(ロストアップデート)

在庫を1減らす処理を、10スレッドから1000回実行します。在庫1000個から始めるので、答えは 0 のはずです。

```kotlin
// FileDbDemo2.kt
import java.io.File
import java.util.concurrent.Executors
import java.util.concurrent.TimeUnit
import java.util.concurrent.atomic.AtomicInteger

fun main() {
    val file = File("stock.txt")
    file.writeText("1000")

    val pool = Executors.newFixedThreadPool(10)
    val errors = AtomicInteger()

    repeat(1000) {
        pool.submit {
            try {
                val current = file.readText().trim().toInt()   // ① 読む
                Thread.sleep(0, 100_000)                       // ② 在庫チェックなどをしているつもり
                file.writeText((current - 1).toString())       // ③ 書く
            } catch (e: Exception) {
                errors.incrementAndGet()
            }
        }
    }

    pool.shutdown()
    pool.awaitTermination(2, TimeUnit.MINUTES)

    println("期待値: 0 / 実際: ${file.readText().trim()} / 例外: ${errors.get()}回")
}
```

**手元の実測値**:

```
期待値: 0 / 実際: 905 / 例外: 341回
```

**1000回在庫を減らしたのに、95個しか減っていません。** さらに 341回は例外で落ちています。

2つの別々の問題が同時に起きています。

**問題A: ロストアップデート(失われた更新)**
Phase 2 でやった競合状態そのものです。

```
時刻  スレッド1              スレッド2
 t1   読む → 1000
 t2                         読む → 1000     ← 1 がまだ書いていない
 t3   書く → 999
 t4                         書く → 999      ← スレッド1の更新が消えた
```

2回減らしたのに1しか減らない。これが900回近く起きたわけです。実務なら**在庫がないのに注文を受け付けた**ということです。

**問題B: 中途半端な状態が読める(torn read)**
341回の例外はこれです。`writeText` は「ファイルを空にしてから書く」ので、**一瞬「空のファイル」が存在します**。そこを別スレッドが読むと
`toInt()` が落ちます。

つまり自分でやるなら、**排他ロック**を実装し、**書き込みは一時ファイル+アトミックなrename**にし、**複数プロセスから触られても壊れないように
**しなければいけません。しかも在庫と注文明細をまとめて更新するなら、複数ファイルにまたがってロックを取る必要があり、今度は*
*デッドロック**を自分で管理する話になります。

> 🔗 **Phase 2 との接続**: 「読んで、考えて、書く」の間に割り込まれると壊れる。この形は Phase 2 の競合状態と完全に同じです。第5章では、この同じ問題を
**MVCC とロック**で DBMS がどう解くのかを見ます。

### 実験3: 途中で落ちるとデータが半分だけ残る(原子性がない)

注文を登録するには、注文ヘッダと注文明細の**両方**を書く必要があります。片方だけ書けた状態はデータとして意味を持ちません。

```kotlin
// FileDbDemo3.kt
import java.io.File
import kotlin.system.exitProcess

fun main(args: Array<String>) {
    val orders = File("orders.csv")
    val items = File("order_items.csv")

    orders.appendText("1001,42,2\n")          // ① 注文ヘッダ

    if (args.contains("--crash")) {
        println("💥 ここで落ちた(電源断 / OOM Killer / デプロイ中の再起動…)")
        exitProcess(1)
    }

    items.appendText("1001,5,1\n1001,9,1\n")  // ② 注文明細
    println("登録完了")
}
```

`--crash` を付けて実行してから、2つのファイルを覗いてください。**明細のない注文**
が残っています。集計すると売上が合わない、出荷リストに出てこない注文が発生する、という状態です。

さらに厄介なのは、`appendText` が返ってきても**まだディスクに書かれていない**ことです。OS のバッファに乗っただけです(Phase
2 でやった話です)。`fsync` を呼ばなければ、電源が落ちた瞬間に消えます。かといって毎回 `fsync` すると劇的に遅くなります。

この「速さと確実さのトレードオフをどう解決するか」が、**第4章の redo ログ(WAL)**の主題です。

### 実験4: 整合性が保てない

CSV には制約という概念がありません。

- ユーザーを削除しても、そのユーザーの注文は残る(**参照先が消えた注文**)
- `price` の列に `"あとで確認"` と書ける
- 同じメールアドレスのユーザーを2回登録できる
- 誰かが Excel で開いて保存し、**列がずれる**

「アプリ側でチェックすればいい」と思うかもしれません。ですが、そのデータに触るのはアプリだけではありません。バッチ処理、管理画面、深夜の手作業のスクリプト、移行ツール。
**どれか1つがチェックを忘れた瞬間に、データは壊れます。**

だから制約は「データの側」に置く必要があります。これが `NOT NULL` / `UNIQUE` / 外部キーの存在理由です。

## 1.2 DBMS が肩代わりしてくれている4つの仕事

実験1〜4で困ったことを整理すると、DBMS の役割がそのまま出てきます。

| 実験 | 困ったこと        | DBMS の解決策                      | 学ぶ章   |
|----|--------------|--------------------------------|-------|
| 1  | 検索が O(n)     | **インデックス**(B+木)、バッファプール        | 第2・3章 |
| 2  | 同時更新で壊れる     | **並行制御**(ロック / MVCC)           | 第5章   |
| 3  | 途中で落ちると半端に残る | **トランザクション**(原子性・耐久性、redoログ)   | 第4章   |
| 4  | データが汚れる      | **制約**(型・NOT NULL・UNIQUE・外部キー) | この章   |

言い換えると、DBMS は **「4つの難しい問題を、みんなが毎回自分で解かなくていいように切り出した共通部品」**です。フレームワークが
HTTP の面倒を見てくれるのと同じ関係です。

そして重要なのは、**DBMS を使っても、これらの問題が消えるわけではない**ことです。

- インデックスは**自分で設計しなければ効かない**(第3章)
- 並行制御は**分離レベルを選ばされる**し、デッドロックは起きる(第5章)
- トランザクションは**境界を自分で引く**必要がある(第6章)

「DBに任せれば安心」ではなく、「**DBが用意した道具を、こちらが正しく使う**」。Phase 4 でやるのは、その道具の使い方です。

> 📌 **コラム: ファイルで十分なケースもある**
> 公平のために書いておくと、DBMS は常に正解ではありません。
> - **設定ファイル**: 同時更新も検索もない → YAML/JSON で十分
> - **アプリケーションログ**: 追記だけ、検索は後で別の仕組み → ファイルが最適(むしろDBに入れると邪魔)
> - **単一プロセスのローカルデータ**: SQLite が最適解になることが多い
> - **巨大なバイナリ(画像・動画)**: S3 等のオブジェクトストレージへ。DBにはURLだけ
>
> 判断軸は「**同時に更新されるか**」「**部分的に検索するか**」「**壊れたら困るか**」です。3つが揃ったらDBMS。

## 1.3 リレーショナルモデル — Phase 0 の集合と関係がここで回収される

さて、DBMS が必要な理由は分かりました。次は「**なぜテーブルという形なのか**」です。

ここで Phase 0 が効いてきます。

### テーブルは「関係(relation)」= タプルの集合

Phase 0 で、直積と関係をやりました。集合 $A$ と $B$ の直積 $A \times B$ の部分集合が**関係**でしたね。

リレーショナルDBのテーブルは、まさにこれです。

- 列 `id` の取りうる値の集合を $D_{id}$、`name` の集合を $D_{name}$、`price` の集合を $D_{price}$ とする
- テーブル `products` は、$D_{id} \times D_{name} \times D_{price}$ の**部分集合**
- 1行 = 1つのタプル $(1, \text{"りんご"}, 300)$

つまり「テーブル = タプルの集合」。これが "**リレーショナル**(関係)" データベースという名前の由来です。表計算ソフトの表に似ているのは見た目だけで、出自は集合論です。

この見方から、**実務で意外と重要な3つの帰結**が出ます。

**帰結1: 行に順序はない**
集合に順序はないので、テーブルの行にも「順番」という属性はありません。`ORDER BY` を付けずに実行した `SELECT` の結果順は*
*保証されません**。「今まで id
順で返ってきていたのに、ある日から順番が変わった」というのは典型的な事故で、原因は実行計画の変化です(第2章)。*
*順序が要るなら必ず `ORDER BY` を書く**、が結論です。

**帰結2: SQL は集合演算**
Phase 0 の言葉で、SQL の基本操作はこう対応します。

| 関係代数         | SQL                              | 意味                     |
|--------------|----------------------------------|------------------------|
| 選択 $\sigma$  | `WHERE`                          | 条件を満たすタプルだけ取る(部分集合を取る) |
| 射影 $\pi$     | `SELECT 列名`                      | 列を絞る                   |
| 結合 $\bowtie$ | `JOIN`                           | 2つの関係を条件付きで直積して絞る      |
| 和・積・差        | `UNION` / `INTERSECT` / `EXCEPT` | 集合演算そのまま               |

だから SQL は「どう探すか」ではなく「**どんな集合が欲しいか**」を書く言語です(宣言的)。「どう探すか」を決めるのは DBMS
側で、それが第2章のオプティマイザです。

**帰結3: 厳密には集合ではなく多重集合(bag)**
実際の SQL のテーブルは重複行を許すので、正確には集合ではなく**多重集合**です。`SELECT DISTINCT`
を書いて初めて集合になります。理論と実装が食い違っている有名な箇所なので、頭の片隅に置いてください。

### キー — どの列で1行を特定するか

- **候補キー**: その値が決まれば1行が一意に決まる列(の組)。複数あってよい
- **主キー(PRIMARY KEY)**: 候補キーの中から「これで代表する」と選んだ1つ
- **外部キー(FOREIGN KEY)**: 他のテーブルの主キーを指す列。「存在しないユーザーの注文」を防ぐ

`users` テーブルなら、`id` と `email` はどちらも候補キーです。そこから `id` を主キーに選ぶ、という関係です。

> ⚠️ **MySQL では主キー選びが性能に直結します**
> InnoDB は主キーの順序でデータ本体を並べて格納します(**クラスタインデックス**)。そのため、
> - `AUTO_INCREMENT` の連番 → 末尾に追記されるので速い
> - ランダムな UUID v4 → **挿入位置がバラバラでページが分裂し、明確に遅くなる**
>
> PostgreSQL にはこの性質がないので、「MySQL 固有の注意点」です。理由は第3章で構造から説明します。今は「MySQLでは主キーの選び方が性能問題になりうる」だけ覚えてください。

### NULL と三値論理 — Phase 0 の命題論理の回収

NULL は「値が無い/不明」を表す特別な印です。そして厄介なことに、**NULL が入ると論理が真・偽の2値ではなくなります**。

Phase 0 でやった命題論理は真偽の2値でしたが、SQL は **真 / 偽 / UNKNOWN** の三値論理です。

```sql
NULL = NULL        -- → UNKNOWN(真ではない!)
NULL <> 1          -- → UNKNOWN
WHERE price = NULL -- → 1行も返らない
WHERE price IS NULL -- → これが正しい書き方
```

`WHERE` 句は「真の行だけ」を返すので、UNKNOWN は捨てられます。ここから実務のハマりどころが生まれます。

```sql
-- 「ステータスがキャンセル以外の注文」を取りたい
SELECT *
FROM orders
WHERE status <> 'canceled';
-- → status が NULL の注文は返ってこない!(UNKNOWN なので)

-- NOT IN の罠: リストに NULL が1つでも混ざると全体が UNKNOWN になり、0件になる
SELECT *
FROM users
WHERE id NOT IN (SELECT user_id FROM orders);
-- → orders.user_id に NULL があると、1行も返らない
```

対策はシンプルです。**そもそも NULL を許さない**。`NOT NULL` + デフォルト値を基本にして、「本当に『不明』という状態があるのか?」を設計時に問う。迷ったら
`NOT NULL` から始めるのが安全です。

## 1.4 正規化と、あえて崩す判断

正規化は「更新のときに困らない形にテーブルを分ける」作業です。名前(1NF/2NF/3NF)は覚えなくていいので、**何が困るのか**
を見てください。

### 困る形の例

注文票をそのまま1行にした、こんなテーブルを考えます。

| order_id | user_name | user_address | items        |
|----------|-----------|--------------|--------------|
| 1001     | 佐藤        | 横浜市西区…       | りんご:2, みかん:1 |
| 1002     | 佐藤        | 横浜市西区…       | ぶどう:1        |

問題を数えてみましょう。

1. **`items` に複数の値が詰まっている** → 「りんごの総売上」を SQL で出せない。文字列を分解するしかない(第1正規形の違反)
2. **佐藤さんの住所が2箇所にある** → 引っ越したとき、**全行を漏れなく更新しないと矛盾する**(更新異常)
3. **注文がまだないユーザーを登録できない**(挿入異常)
4. **注文を消すとユーザー情報も消える**(削除異常)

これを解くのが正規化で、やることは1つ、**「1つの事実を1箇所にだけ持つ」**です。

```
users(id, name, address)
orders(id, user_id, ordered_at)
order_items(id, order_id, product_id, quantity)
products(id, name, price)
```

住所は `users` に1箇所だけ。だから更新は1行で済み、矛盾しようがありません。

正規形の名前と対応だけ一応載せます(**暗記不要**):

| 正規形 | ざっくり何を禁止するか                   |
|-----|-------------------------------|
| 1NF | 1つのセルに複数の値を詰めること              |
| 2NF | 複合キーの**一部**にだけ依存する列があること      |
| 3NF | キー以外の列に依存する列があること(住所→郵便番号 など) |

### では、いつ崩すのか

ここが実務の勘所です。**「正規化を崩す」ように見えて、実は崩していないケース**が非常に多いので、そこを区別します。

**ケースA: これは崩していない(スナップショット)**

`order_items` に `unit_price`(注文時の単価)を持つのは、`products.price` の重複コピーに見えます。しかし違います。

- `products.price` = **今の**価格
- `order_items.unit_price` = **注文した時点の**価格

これは**別の事実**です。もし持たずに毎回 `products` と JOIN して価格を出すと、**商品の値上げをした瞬間に、過去の注文金額が全部書き換わります
**。実務でこれをやると請求金額が合わなくなり、確実に事故になります。

同じ理屈で、注文時点の届け先住所、注文時点の商品名も注文側に保存すべきです。「履歴として意味のある値は、その時点でコピーする」。これは正規化違反ではなく
**正しい設計**です。

**ケースB: これは意図的に崩している(性能のため)**

- 記事テーブルに `comment_count` を持つ(毎回 `COUNT(*)` すると重いので)
- 一覧表示用に JOIN 結果を1テーブルにまとめておく

こちらは本当に重複なので、**整合性を保つ責任がアプリ側に移ります**。コメント削除時にカウントを減らし忘れると、表示がずれます。だから
**測って重いと分かってから**やるべきで、最初からやるものではありません。

> 💼 **実務の障害例**
> 「特定ユーザーの住所だけ古いまま」という問い合わせが来て調べたら、住所が `users` と `orders`
> と配送テーブルの3箇所にあり、更新しているのは2箇所だけだった——というのは典型的な障害です。原因は「どれが正なのか誰も分からなくなっていた」こと。
**1つの事実は1箇所**、が守れているかは、設計レビューで最初に見るポイントです。

## 1.5 MySQL は内部で何をしているのか

DB の必要性とデータの形が分かったので、いよいよ MySQL 自体の構造を見ます。**この図が Phase 4 全体の地図になります。**

```
   Kotlin アプリ(MyBatis / JDBC / HikariCP)
         │
         │  TCP :3306(+ TLS)      ← Phase 3 第3・6章
         ▼
  ┌──────────────────────────────────────────┐
  │ ① 接続層                                  │
  │    認証・接続ごとのスレッド割り当て       │  ← 第6章(プール枯渇)
  ├──────────────────────────────────────────┤
  │ ② パーサ                                  │
  │    SQL文字列 → 構文木、文法チェック        │
  ├──────────────────────────────────────────┤
  │ ③ オプティマイザ                          │
  │    統計情報を見て「実行計画」を決める     │  ← 第2章の主役
  ├──────────────────────────────────────────┤
  │ ④ エグゼキュータ                          │
  │    計画に従ってストレージエンジンを叩く   │
  ├──────────────────────────────────────────┤
  │ ⑤ ストレージエンジン(InnoDB)             │
  │    バッファプール(メモリキャッシュ)     │  ← 第3章
  │    B+木(インデックス)                   │  ← 第3章
  │    ロック / MVCC / undoログ               │  ← 第5章
  │    redoログ(WAL)                        │  ← 第4章
  └──────────────────────────────────────────┘
         │
         ▼
   ディスク(.ibd / redoログ / binlog)   ← Phase 2、binlogは第7章
```

**注目すべきは ⑤ が差し替え可能な部品として分離していること**です。MySQL は「SQL を解釈する部分」と「実際にデータを読み書きする部分」が分かれていて、後者を
**ストレージエンジン**と呼びます。歴史的に MyISAM 等が使われましたが、**現在は InnoDB 一択**です(トランザクションと行ロックを持つのが
InnoDB だけなので)。

なので Phase 4 でこれから深掘りするのは、ほとんど ⑤ の中身です。「MySQL を学ぶ」というより「**InnoDB を学ぶ**
」と思っておくと見通しが良くなります。

> 🔗 **Phase 3 との接続**: ① の入口は **ソケット**です。Phase 3 第7章で書いたソケットプログラミングの、サーバ側が
> MySQL、クライアント側が JDBC ドライバ。「接続確立が高コストだから使い回す」(第8章)がそのまま **HikariCP** の話になります。1.6
> の最後で、この接続を実際に目で見ます。

### スキーマを作る

Phase 4 全体で使う、EC サイトの最小構成です。

```sql
-- users: 100,000 件
CREATE TABLE users
(
    id         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    email      VARCHAR(255) NOT NULL,
    name       VARCHAR(100) NOT NULL,
    created_at DATETIME(6)     NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
    PRIMARY KEY (id),
    UNIQUE KEY uk_users_email (email)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;

-- products: 1,000,000 件
CREATE TABLE products
(
    id    BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    name  VARCHAR(200) NOT NULL,
    price INT          NOT NULL, -- 円。整数で持つ(理由は下記)
    stock INT          NOT NULL,
    PRIMARY KEY (id)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;

-- orders: 500,000 件
CREATE TABLE orders
(
    id           BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    user_id      BIGINT UNSIGNED NOT NULL,
    status       VARCHAR(20) NOT NULL,
    total_amount INT         NOT NULL,
    ordered_at   DATETIME(6)     NOT NULL,
    PRIMARY KEY (id),
    KEY          idx_orders_user_id (user_id),
    CONSTRAINT fk_orders_user FOREIGN KEY (user_id) REFERENCES users (id)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;

-- order_items: 1,000,000 件
CREATE TABLE order_items
(
    id         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    order_id   BIGINT UNSIGNED NOT NULL,
    product_id BIGINT UNSIGNED NOT NULL,
    quantity   INT NOT NULL,
    unit_price INT NOT NULL, -- 注文時点の価格(1.4 のスナップショット)
    PRIMARY KEY (id),
    KEY        idx_order_items_order_id (order_id)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;
```

**設計上の注意点を3つ**:

1. **金額を `INT`(円)で持っている**。`FLOAT` / `DOUBLE` は絶対に使いません。二進浮動小数点は 0.1
   を正確に表現できないので、足し算を繰り返すと1円ずれます。小数が必要なら `DECIMAL` を使います。(Phase 2
   で数値表現を扱ったなら、その回収です)
2. **`ordered_at` と `products.name` にわざとインデックスを張っていません**
   。第2章と第3章で、これを追加して前後を比較するためです。「遅い状態」を残しておくのが目的です
3. **`order_items` には外部キーを付けていません**。1.4
   の議論どおり付けるべきですが、第5章でロックの挙動を素直に観察したいので外しています(
   外部キーは裏で追加のロックを取ります)

### データを投入する

                           UNION ALL
                           SELECT n + 1

         CROSS JOIN (SELECT 1 UNION ALL SELECT 2) AS two;

SET
foreign_key_checks = 1;

## 1.7 「DBだから速い」のではない — 一番大事な実測

いよいよ CSV と比較します。実験1 では 100万行から1件取り出すのに **157ms** かかりました。

```sql
-- ① 主キーで1件
SELECT *
FROM products
WHERE id = 999999;

-- ② 主キー以外(インデックスなし)で1件
SELECT *
FROM products
WHERE name = 'item999999';
```

**それぞれ2回ずつ**実行してください(1回目はディスクから読むので、2回目がバッファプールに乗った状態の値です)
。手元の結果はこうなりました。

```
① SELECT * FROM products WHERE id = 999999;
   1 row in set (0.00 sec)

② SELECT * FROM products WHERE name = 'item999999';
   1 row in set (0.21 sec)
```

**ここが第1章で最も持ち帰ってほしい事実です。**

- ① 主キー検索は **測定できないほど速い**(1ミリ秒未満)
- ② インデックスのない列の検索は **0.21秒** — **CSV の全行走査(0.157秒)とほぼ同じ**

②は MySQL が内部で100万行を全部読んでいます。やっていることは実験1の Kotlin コードと同じです。つまり、

> **DBMS に入れたから速くなるのではありません。**
> **インデックスがある検索だけが速く、無い検索は CSV と同じ速さです。**

これが第2章・第3章の全体の動機です。「DB が遅い」と言われる障害の大半は、**索引が効いていないクエリ**
です。そして「効いているかどうか」を確認する道具が `EXPLAIN` で、次章の主題になります。

最後に、②が本当に全行読んでいることを覗いてみましょう。詳しい読み方は第2章でやるので、いまは雰囲気だけで結構です。

```sql
EXPLAIN
SELECT *
FROM products
WHERE name = 'item999999';
```

```
+----+-------------+----------+------+---------------+------+---------+------+--------+----------+-------------+
| id | select_type | table    | type | possible_keys | key  | key_len | ref  | rows   | filtered | Extra       |
+----+-------------+----------+------+---------------+------+---------+------+--------+----------+-------------+
|  1 | SIMPLE      | products | ALL  | NULL          | NULL | NULL    | NULL | 996--- |    10.00 | Using where |
+----+-------------+----------+------+---------------+------+---------+------+--------+----------+-------------+
```

`type` が **`ALL`**。これが「全行読みます」の宣言です。そして `rows` がおよそ100万。一方 ①は:

```sql
EXPLAIN
SELECT *
FROM products
WHERE id = 999999;
```

`type` が **`const`**、`rows` が **1**。100万行のうち1行だけ触れば済む、と言っています。

**この `type` 列と `rows` 列を読めるようになるだけで、実務のクエリ調査能力が一段上がります。** 次章でここを徹底的にやります。

### 演習1 — 正規化

以下のテーブルの問題点を挙げ、分割してください。

| id | user_email | user_name | product_names | total | shop_name | shop_tel |
|----|------------|-----------|---------------|-------|-----------|----------|
| 1  | a@x.com    | 田中        | りんご,みかん       | 800   | 横浜店       | 045-xxx  |
| 2  | a@x.com    | 田中        | ぶどう           | 500   | 横浜店       | 045-xxx  |

<details>
<summary>解答</summary>

**問題点**

1. `product_names` に複数値が詰まっている(1NF違反)→ 商品別の集計ができない
2. `user_name` が注文ごとに重複 → 改名時に更新漏れ(更新異常)
3. `shop_tel` が `shop_name` に依存している(3NF違反)→ 電話番号変更で全注文行を更新することになる
4. 注文のないユーザー・店舗を登録できない(挿入異常)

**分割案**

```
users(id, email, name)
shops(id, name, tel)
orders(id, user_id, shop_id, total, ordered_at)
order_items(id, order_id, product_id, quantity, unit_price)
products(id, name, price)
```

**追加で考えてほしい点**: `orders.total` は `order_items`
から計算できるので、厳密には冗長です。ただし「注文時に確定した請求額」として保存する意味があり、後から明細の単価がずれても請求額が変わらない保証になります。これは
1.4 のケースA(スナップショット)に該当し、**残す判断が妥当**です。「計算できるから消すべき」と機械的に判断しないのがポイントです。
</details>

### 演習2 — NULL

`users` に `deleted_at DATETIME NULL`(退会日時、現役会員は NULL)があるとします。次のクエリで「現役会員」は取れますか?

```sql
SELECT *
FROM users
WHERE deleted_at = NULL;
SELECT *
FROM users
WHERE deleted_at <> '2024-01-01';
```

<details>
<summary>解答</summary>

**どちらも取れません。**

1つ目: `= NULL` は常に UNKNOWN と評価され、`WHERE` は真の行だけを返すので **0件**です。正しくは
`WHERE deleted_at IS NULL`。

2つ目: `deleted_at` が NULL の行は `NULL <> '2024-01-01'` → UNKNOWN なので除外されます。つまり**現役会員が全員落ちる**
、意図と正反対の結果です。

**実務的な対策**: 退会フラグは `is_deleted BOOLEAN NOT NULL DEFAULT FALSE` と `deleted_at` を併用する、あるいは
`deleted_at NOT NULL DEFAULT '9999-12-31'` にして NULL を排除する設計もあります。いずれにせよ「NULL
を含む列に不等号を書いていないか」は、レビューで見るべき定番の観点です。
</details>

### 演習3 — 実測して考える

`products.name` にインデックスを追加して、1.7 の②を測り直してください。

```sql
CREATE INDEX idx_products_name ON products (name);
SELECT *
FROM products
WHERE name = 'item999999';
```

そのうえで:(a) 何倍速くなったか (b) `EXPLAIN` の `type` と `rows` はどう変わったか (c) **このインデックスの代償は何か**

<details>
<summary>解答</summary>

**(a)** 0.2秒台 → 0.00秒(1ms未満)。100倍以上のオーダーで速くなります。

**(b)** `type` が `ALL` → `ref`(または `const`)、`rows` が約100万 → 1。**「触る行数が減った」ことが速さの正体**
です。ここが第3章の核心につながります。

**(c) 代償は3つあります。**

1. **容量**: インデックスは別のB+木として保存されるので、ディスクとバッファプールを消費します。`information_schema.tables`
   の `index_length` で確認できます
2. **書き込みが遅くなる**: INSERT / UPDATE / DELETE のたびにインデックスも更新が必要です。インデックスが10個あれば、1行の追加で11本の木を更新します
3. **バッファプールの圧迫**: インデックスがメモリを食うと、他のデータがキャッシュから追い出されます

だから「とりあえず全列にインデックス」は間違いです。**読む回数と書く回数のバランスで決めます**。第3章で設計方針をやります。

> 測り終わったら、このインデックスは **`DROP INDEX idx_products_name ON products;` で消しておいてください。**
> 第2章で「遅い状態」から始めたいので。
</details>

### 演習4 — 設計判断

次の3つのデータについて、DBMS を使うべきか、ファイルで十分かを判断し、理由を述べてください。

1. アプリのアクセスログ(1日1000万行、後で分析したい)
2. 為替レート(1分ごとに更新、複数サーバから参照、履歴も残す)
3. 機能フラグの設定(10項目、変更は月1回、デプロイ時に読むだけ)

<details>
<summary>解答例</summary>

**1. アクセスログ → まずファイル(あるいはログ基盤)**
追記のみで同時更新がなく、書き込み量が膨大です。RDB に毎行 INSERT
するとログ書き込みのコストが支配的になり、本来のトランザクションを圧迫します。ファイルに吐いて、後でまとめて分析用ストア(
BigQuery / S3+Athena / ClickHouse 等)に流すのが定石です。**「同時更新されない」「1件ずつの整合性が重要でない」**が判断根拠です。

**2. 為替レート → DBMS**
複数サーバから同時に読まれ、更新もあり、履歴に整合性が必要。1.1 の4つの問題が全部当てはまります。加えて「最新の1件」を高速に引く必要があるので、インデックスも欲しい。

**3. 機能フラグ → ファイルで十分**
10項目、月1回更新、読むだけ。DBMS を挟むと、むしろ「DB が落ちたらアプリが起動しない」という依存を増やすだけです。設定ファイルか環境変数が適切です。

**判断軸(再掲)**: 同時に更新されるか / 部分的に検索するか / 壊れたら困るか。**3つ揃ったら DBMS**。
</details>

### 演習5 — 少し難しい

実験2 のロストアップデートを、**ファイルのまま**正しく動くように直してください。そのうえで「DBMS
を使う場合と比べて、何が足りないか」を考えてください。

<details>
<summary>解答例</summary>

同一プロセス内なら、ロックをかけるだけで直ります。

```kotlin
val lock = Any()
// ...
pool.submit {
    synchronized(lock) {
        val current = file.readText().trim().toInt()
        file.writeText((current - 1).toString())
    }
}
```

これで期待値どおり 0 になります。**ただし足りないものが山ほどあります。**

1. **別プロセスには効かない**。バッチや別サーバから触られたら壊れます。`FileChannel.lock()`(OSのファイルロック)が必要
2. **原子性がない**。在庫ファイルと注文ファイルを両方更新する途中で落ちたら、やはり半端に残ります
3. **耐久性がない**。`fsync` を呼ばないと電源断で消えます
4. **並行性が最悪**。`synchronized` はファイル全体を1つのロックで守るので、**別の商品の在庫更新まで待たされます**。DBMS
   は行単位でロックするので、違う行なら並行に進めます(第5章)
5. **デッドロックを自分で管理**することになります。DBMS は検出して片方を自動的に巻き戻します

つまり「正しく動かす」だけなら書けますが、「**正しく、速く、複数プロセスから、落ちても壊れない**」を全部満たすのが極めて難しい。だから
DBMS という専門部品があるわけです。
</details>

## 次章の予告 — 第2章 SQL はどう実行されるのか

1.7 で、`type = ALL` なら遅く、`type = const` なら速いことを見ました。次章では、この**実行計画がどう決まるのか**を扱います。

- SQL(「何が欲しいか」)から実行計画(「どう取るか」)への変換
- `EXPLAIN` の全列の読み方 — `type` / `key` / `rows` / `filtered` / `Extra`
- `EXPLAIN ANALYZE` で見積りと実測を比べる
- オプティマイザは統計情報を見て判断する → **統計が古いと計画を間違える**
- 結合アルゴリズム(Nested Loop / Hash Join)
- 実務: 「昨日まで速かったクエリが今日から遅い」の原因調査

第2章を終えると、**「このクエリが遅い理由」を推測ではなく根拠で言えるようになります**。実務で一番使う武器です。
