## 4.1 トランザクションとは「まとめて全部か、全部なしか」

### 身近な例

銀行振込を考えます。A さんの口座から1万円引いて、B さんの口座に1万円足す。この2つの操作の**間**でシステムが落ちたら、1万円が世界から消えます。

第1章の実験3で、まったく同じことをやりました。注文ヘッダを書いて、明細を書く前に落ちる。**明細のない注文**が残りましたね。

トランザクションとは、**複数の操作を「1つの不可分な操作」として扱う仕組み**です。

```
全部成功する  →  全部反映される(COMMIT)
1つでも失敗   →  全部なかったことになる(ROLLBACK)
```

**「途中の状態」が外から見えることはありません。**

### 触ってみる

```sql
SELECT id, total_amount FROM orders WHERE id = 1;

START TRANSACTION;                                    -- BEGIN でも同じ
UPDATE orders SET total_amount = 999999 WHERE id = 1;
SELECT id, total_amount FROM orders WHERE id = 1;     -- 999999 に見える
ROLLBACK;
SELECT id, total_amount FROM orders WHERE id = 1;     -- 元に戻っている
```

**別のターミナルからもう1つ接続**して、`ROLLBACK` する前に同じ `SELECT` を実行してみてください。

```bash
docker compose exec mysql mysql -uroot -prootpass cs_study
```

```sql
SELECT id, total_amount FROM orders WHERE id = 1;   -- 元の値のまま!
```

**セッション1では 999999 に見えているのに、セッション2では元の値**です。これが「途中の状態は外から見えない」ということで、ACID の **I(分離性)** に当たります。第5章の主題なので、今は「そうなる」だけ確認してください。

### autocommit — 実は毎回トランザクションを張っている

```sql
SELECT @@autocommit;   -- 1(既定でON)
```

MySQL は既定で **autocommit が ON** です。つまり、

```sql
UPDATE orders SET status = 'paid' WHERE id = 1;
```

と書いた1文は、内部的にはこう扱われています。

```sql
START TRANSACTION;
UPDATE orders SET status = 'paid' WHERE id = 1;
COMMIT;   -- ← 自動
```

**「トランザクションを使っていない」状態は存在しません。** 1文ごとにトランザクションが張られているだけです。

これが実務で効いてくる場面が2つあります。

1. **1万件の INSERT を1件ずつ実行すると、1万回のコミットが発生する** → 4.4 で実測します
2. **`START TRANSACTION` で明示的に囲むと、autocommit は一時的に無効化される** → 囲んだ範囲が1つの単位になる

第6章の Kotlin/MyBatis では、この autocommit をどう制御するかが直接のテーマになります。

## 4.2 ACID を分解する

トランザクションが満たすべき性質として、頭文字を取って ACID と呼ばれる4つが挙げられます。ただし、**4つは対等ではありません**。ここを整理しておくと後が楽です。

| | 名前 | 内容 | 実装しているもの |
|---|---|---|---|
| **A** | 原子性 (Atomicity) | 全部か、全部なしか | **undo ログ**(4.5) |
| **C** | 一貫性 (Consistency) | 矛盾した状態にしない | 制約 + **アプリの責務** |
| **I** | 分離性 (Isolation) | 並行実行しても互いに邪魔しない | ロック / MVCC(**第5章**) |
| **D** | 耐久性 (Durability) | コミットしたら消えない | **redo ログ**(4.3) |

### C だけ性質が違う

A・I・D は「DBMS がこう動く」という**機構の話**ですが、**C は「結果としてこうあってほしい」という目標**です。

例えば「口座残高の合計は変わらない」という一貫性は、MySQL が保証してくれるものではありません。`UPDATE` を1つ書き忘れれば、原子性も分離性も耐久性も守られたまま、残高の合計は狂います。

DB が提供するのは、

- 型・`NOT NULL`・`UNIQUE`・外部キーといった**宣言できる制約**(第1章)
- A・I・D という**土台**

であって、**業務ルール上の正しさはアプリが担保します**。「ACID だから安心」と言うとき、実は C はあまり保証されていない、という点は覚えておいてください。

この章では **A と D**、次章で **I** を扱います。

## 4.3 耐久性はどう実現されるのか — WAL(先行書き込みログ)

### まず問題を正確に置く

`UPDATE orders SET status = 'paid' WHERE id = 1;` を実行したとき、第3章で学んだとおり InnoDB は**バッファプール上のページを書き換えるだけ**です。

```
メモリ(バッファプール)  : ページ #42 → status='paid'  ← 書き換え済み
ディスク(.ibd ファイル) : ページ #42 → status='pending' ← 古いまま!
```

この状態で電源が落ちたら、変更は消えます。では**コミットのたびにページをディスクに書けばいい**のでは?

**それでは遅すぎます。** 理由は3つ。

1. **ランダムI/O**: 更新した行があちこちのページに散らばっていれば、ディスク上の離れた位置に何度も書くことになる
2. **書きすぎ**: 100バイトの行を1つ書き換えるために、**16KBのページ全体**を書く必要がある
3. **`fsync` が高コスト**: 「本当にディスクに届いた」ことを保証する `fsync` は、ミリ秒単位の時間がかかる(Phase 2 の話です)

### 発想の転換 — 「変更した結果」ではなく「何をしたか」を記録する

そこで InnoDB はこうします。

> **ページ本体は後で書く。その代わり、「どのページをどう変えたか」という記録だけを、コミット時に確実に保存する。**

この記録が **redo ログ**、この方式が **WAL(Write-Ahead Logging / 先行書き込みログ)**です。

redo ログが速い理由は明快です。

| | ページ本体 | redo ログ |
|---|---|---|
| 書く場所 | あちこち(**ランダム**) | ログファイルの末尾(**シーケンシャル追記**) |
| 書く量 | 16KB × 変更したページ数 | 変更内容だけ(数十〜数百バイト) |

**シーケンシャルな追記は、ランダム書き込みより桁違いに速い**のです。第1章の CSV への `appendText` が速かったのと同じ理屈です。

### 時系列で追う

```
   ① UPDATE 実行
        ├─ バッファプールのページを書き換え(メモリ上)
        └─ 変更内容を redo ログバッファに追記(メモリ上)
   ② COMMIT
        └─ redo ログバッファをファイルに書き、fsync   ← ここだけディスクを待つ
        └─ クライアントに「成功」を返す
   ③ しばらく後(バックグラウンド)
        └─ 書き換わったページ(ダーティページ)をディスクへ書き出す
```

**②が終わった時点で耐久性は満たされています。** ③の前に電源が落ちても、redo ログに「ページ #42 をこう変えた」と残っているので、**起動時にやり直せる**からです(4.6)。

これが「メモリを書き換えただけなのに、なぜコミット完了と言えるのか」への答えです。**ページは失われても、やり直す手順書が残っている**。

### 実物を見る

```sql
SHOW ENGINE INNODB STATUS\G
```

出力の `LOG` セクションを探してください。

```
---
LOG
---
Log sequence number          1245789302
Log buffer assigned up to    1245789302
Log buffer completed up to   1245789302
Log written up to            1245789302
Log flushed up to            1245781920
Added dirty pages up to      1245789302
Pages flushed up to          1198340221
Last checkpoint at           1198340221
```

**LSN(Log Sequence Number)**は、redo ログに書かれたバイト数の通し番号です。「今どこまで進んでいるか」を表します。注目すべきは3つ。

- **`Log sequence number`** — 現在位置。更新すると増えます
- **`Log flushed up to`** — **ディスクに `fsync` 済みの位置**。ここまでは電源が落ちても残る
- **`Last checkpoint at`** — ダーティページの書き出しが完了した位置(4.6)

`UPDATE` を何度か実行してから再度見ると、LSN が進んでいるのが分かります。**手を動かして確かめてください。**

ファイル本体も覗けます。

```bash
docker compose exec mysql ls -la /var/lib/mysql/#innodb_redo/
```

```sql
SELECT @@innodb_redo_log_capacity / 1024 / 1024 AS mb;   -- 既定 100MB
```

固定サイズの領域を**輪のように使い回します**(循環ログ)。だから無限に増えることはありません。

## 4.4 `fsync` のコスト — 速さと確実さのトレードオフ

### 実測してみる

「コミットのたびに `fsync`」がどれくらい高コストか、実際に測ります。ストアドプロシージャでループを回します。

```sql
CREATE TABLE bench (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
  v  INT NOT NULL
) ENGINE = InnoDB;

DELIMITER //
CREATE PROCEDURE bench_insert(IN n INT, IN use_tx BOOLEAN)
BEGIN
  DECLARE i INT DEFAULT 0;
  IF use_tx THEN START TRANSACTION; END IF;
  WHILE i < n DO
    INSERT INTO bench (v) VALUES (i);
    SET i = i + 1;
  END WHILE;
  IF use_tx THEN COMMIT; END IF;
END//
DELIMITER ;
```

3パターン測ります。

```sql
-- ① 1件ずつコミット(autocommit のまま)
TRUNCATE bench;
CALL bench_insert(10000, FALSE);

-- ② 1万件を1トランザクションで
TRUNCATE bench;
CALL bench_insert(10000, TRUE);

-- ③ fsync を緩めて、1件ずつコミット
SET GLOBAL innodb_flush_log_at_trx_commit = 2;
TRUNCATE bench;
CALL bench_insert(10000, FALSE);
SET GLOBAL innodb_flush_log_at_trx_commit = 1;   -- 必ず戻す!
```

**参考値**(環境差が非常に大きい項目です。**自分の値を記録してください**):

```
① 1件ずつコミット        : 10〜30秒
② 1トランザクション      : 0.3〜1秒        ← 数十倍速い
③ 1件ずつ + flush=2      : 1〜3秒
```

> 📌 Docker Desktop(macOS/Windows)では仮想ファイルシステムを経由するため、`fsync` の挙動がホストと異なります。**桁の違いが観察できれば十分**です。

### なぜ数十倍も違うのか

①は**1万回の `fsync`** を実行しています。1回あたり1〜3ms かかるとすれば、それだけで10〜30秒です。

②は `fsync` が**コミット時の1回だけ**。1万件分の redo ログをまとめて書きます。

**「コミット回数 = `fsync` 回数」であり、`fsync` 回数が書き込み性能を決めます。** これがこの節の結論です。

### `innodb_flush_log_at_trx_commit` の3つの値

```sql
SELECT @@innodb_flush_log_at_trx_commit;   -- 既定 1
```

| 値 | 動作 | 落ちたときに失うもの |
|---|---|---|
| **1**(既定) | コミットごとにログを書き、`fsync` | **何も失わない**(ACID準拠) |
| **2** | コミットごとに書くが、`fsync` は毎秒 | **OSごと落ちたら**約1秒分。MySQLプロセスだけの死なら失わない |
| **0** | 毎秒まとめて書いて `fsync` | MySQL が落ちただけでも約1秒分 |

**判断基準は「1秒分の更新を失っても許容できるか」**です。

- 課金・在庫・受注 → **1一択**
- アクセス解析の集計、リトライで再生成できるデータ → 2 を検討する価値あり
- 開発環境・テストデータ投入 → 2 でも 0 でも構わない

「速くしたいから 0 にする」という判断は、**失っても構わないデータかどうかを確認してから**にしてください。

### グループコミット — MySQL の側の工夫

「同時に100接続がコミットしたら、`fsync` が100回?」と思うかもしれませんが、そうはなりません。InnoDB は**同時期のコミットをまとめて1回の `fsync` で処理**します(グループコミット)。

だから**同時実行数が多いほど、1コミットあたりの `fsync` コストは下がります**。逆に言うと、**単一スレッドで大量にコミットするのが最悪のパターン**です。①の実験がまさにそれでした。

### binlog も `fsync` している

第1章で `log_bin` を有効にしました。第7章のレプリケーションで使う **binlog** です。

```sql
SELECT @@sync_binlog;   -- 既定 1
```

これも既定でコミットごとに `fsync` します。つまり**コミット1回につき `fsync` が2回**(redo と binlog)。

しかも両者が食い違うと困る(redo には反映されたのに binlog に無い = レプリカにだけ伝わらない)ので、InnoDB は**内部的に2相コミット**を行って整合させています。第8章でやる分散トランザクションの 2PC が、実は MySQL の内部で毎回動いているわけです。

> 💡 「MySQL は binlog を切ると速くなる」と言われるのは、この `fsync` 1回分が減るからです。ただしレプリケーションもポイントインタイムリカバリもできなくなるので、本番では通常切りません。

## 4.5 undo ログ — 原子性とロールバック

redo は「やり直す」ためのログでした。**「元に戻す」ためのログ**が別にあります。**undo ログ**です。

### 仕組み

行を更新するとき、InnoDB は**更新前の値**を undo ログに退避します。

```
UPDATE orders SET status = 'paid' WHERE id = 1;

  undo ログ: 「id=1 の status を 'pending' に戻せ」   ← 旧値
  ページ    : status = 'paid' に書き換え
```

`ROLLBACK` されたら、undo ログを逆順に適用して元に戻します。これが**原子性(A)の実装**です。

### 実務で効いてくる3つの帰結

**① ロールバックはコミットより遅いことがある**

コミットは「redo を `fsync` して終わり」ですが、ロールバックは**変更した行を1つずつ戻す実作業**が必要です。

```sql
START TRANSACTION;
UPDATE orders SET status = 'x';   -- 50万行を更新
ROLLBACK;                          -- 戻すのに時間がかかる
```

**実際にやって、UPDATE とROLLBACK それぞれの時間を測ってみてください。**

💼 **実務での意味**: 「長時間動いているバッチを `KILL` したのに、いつまでも終わらない」という状況の正体がこれです。KILL した瞬間からロールバックが始まり、**進行状況によっては元の処理と同じくらい時間がかかります**。しかも待つしかありません(強制終了させると、起動時に同じロールバックをやり直すだけです)。

**② 長いトランザクションは undo を溜める**

undo ログは「まだ誰かが必要としている間」は消せません。**トランザクションを開いたまま放置すると、その間の全ての旧値が保持され続けます**。

```sql
SHOW ENGINE INNODB STATUS\G
```

`TRANSACTIONS` セクションの先頭付近に、こんな行があります。

```
History list length 1523
```

**未パージの undo レコード数**です。通常は数百〜数千で推移しますが、これが数十万〜数百万に膨れていたら、**どこかで長時間トランザクションが開きっぱなし**です。放置するとディスクを食い潰し、読み取り性能も落ちます。

犯人はここで探せます。

```sql
SELECT trx_id, trx_state, trx_started,
       TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS sec,
       trx_rows_modified, trx_query
FROM information_schema.innodb_trx
ORDER BY trx_started;
```

**開始から数分以上経っているトランザクションは、ほぼ例外なく異常**です。第9章の調査手順で再登場します。

**③ undo は MVCC の土台になる**

ここが次章への橋です。undo ログには「更新前の値」が残っています。ということは、

> **「あるトランザクションが始まった時点の値」を、undo を辿って復元できる。**

これが第5章の **MVCC(多版型同時実行制御)**です。「読み取りがロックで待たされない」のは、**書き換えられた行の古い版が undo に残っているから**です。

undo は「ロールバック用」だけの仕組みではなく、**分離性(I)の実装でもある**わけです。

## 4.6 クラッシュリカバリ — 落ちた後に何が起きるか

### チェックポイント

redo ログは循環バッファなので、**古い部分はいつか上書きされます**。上書きしてよいのは「そのログが指すページが、既にディスクに書かれている」場合だけです。

そこで InnoDB は定期的にダーティページを書き出し、「ここまでのログはもう不要」という印を進めます。これが**チェックポイント**で、4.3 で見た `Last checkpoint at` の値です。

```
Log sequence number   1245789302   ← 現在位置
Last checkpoint at    1198340221   ← ここまでのページは書き出し済み
                      ↑
        この差(checkpoint age)が大きいほど、復旧に時間がかかる
```

⚠️ **差が redo ログ容量に迫ると、MySQL は書き込みを意図的に遅くします**(非同期フラッシュ)。「大量更新の途中で急に書き込みが詰まる」という現象の原因の1つです。`innodb_redo_log_capacity` を増やすと緩和できますが、その分クラッシュ復旧が長くなります。

### 復旧の2段階

電源が落ちた瞬間、こういう状態です。

- コミット済みだがページに反映されていない変更がある
- **未コミットなのにページに反映されてしまった**変更もある(ダーティページはコミット前でも書き出されます)

だから復旧は2段階です。

```
【第1段階】ロールフォワード(redo を前進適用)
  最後のチェックポイント以降の redo ログを全部適用する
  → コミット済みの変更が復活する
  → ただし、未コミットの変更も一緒に復活してしまう

【第2段階】ロールバック(undo を適用)
  復活した中から「コミットされていなかったトランザクション」を特定し、
  undo ログで巻き戻す
  → 未コミットの変更が消える
```

**redo で全部やり直してから、undo で余計な分を戻す。** この順序が重要です。

### 部分書き込み問題 — doublewrite buffer

もう1つ、地味だが致命的な問題があります。

**16KBのページを書いている途中で電源が落ちたら?** OS やディスクのブロックサイズは4KBなので、**16KBのうち8KBだけ書かれた壊れたページ**ができる可能性があります(torn page)。

こうなると redo ログを適用しようにも、**適用先のページ自体が壊れている**ので復旧できません。

対策が **doublewrite buffer** です。ページを本来の位置に書く前に、まず**専用の連続領域に書いておきます**。復旧時にページが壊れていたら、そちらから復元します。

```sql
SELECT @@innodb_doublewrite;   -- 既定 ON
```

書き込みが2回になりますが、doublewrite 領域への書き込みは連続領域へのシーケンシャル書き込みなので、コストは思ったほど高くありません。**切ってはいけません。**

> 🔗 **第1章との接続**: 実験2で「`writeText` の途中を読むと壊れたデータが見える」という torn read を体験しました。これはその**物理層版**です。同じ問題が、レイヤを変えて何度も現れます。

### 実験: 本当にロールバックされるか

**実際に殺してみましょう。** これが第1章の実験3への回答になります。

```sql
-- ① 現在値を確認
SELECT id, status, total_amount FROM orders WHERE id IN (1, 2);

-- ② コミットする変更
UPDATE orders SET total_amount = 111111 WHERE id = 1;   -- autocommit で即コミット

-- ③ コミットしない変更
START TRANSACTION;
UPDATE orders SET total_amount = 222222 WHERE id = 2;
SELECT id, total_amount FROM orders WHERE id IN (1, 2);   -- 両方変わって見える
-- COMMIT はしない! この状態のまま次へ
```

**別のターミナル**から、電源を引き抜きます。

```bash
docker compose kill mysql      # SIGKILL。graceful shutdown を挟まない
docker compose start mysql
docker compose logs --tail=50 mysql
```

ログに復旧の痕跡が出ます。

```
[InnoDB] Starting crash recovery.
[InnoDB] Applying a batch of ... redo log records ...
[InnoDB] Rolling back trx with id ..., 1 rows to undo
[InnoDB] Crash recovery finished.
```

**`Starting crash recovery` と `Rolling back` が出ていることを確認してください。** 4.6 で説明した2段階が、そのままログに出ています。

そして値を見ます。

```sql
SELECT id, total_amount FROM orders WHERE id IN (1, 2);
```

```
id=1 → 111111   ← コミット済みなので生き残った(耐久性 D)
id=2 → 元の値   ← 未コミットなので巻き戻された(原子性 A)
```

**A と D が同時に確認できました。** 第1章の CSV では「明細のない注文」が残ってしまいましたが、DB では**中途半端な状態が残りません**。

## 4.7 実務への接続

### ① 大量 INSERT が遅いとき

4.4 で見たとおり、原因はほぼ**コミット回数**です。対策を効果の大きい順に。

1. **まとめてコミットする**(1件ずつ → 1000件ごと)。効果は数十倍
2. **複数行 INSERT にする** — `INSERT INTO t VALUES (...), (...), (...)`。ネットワーク往復も減る(Phase 3 の話です)
3. **JDBC のバッチを有効にする** — 第6章で `rewriteBatchedStatements=true` を実測します
4. **一時的にインデックスを外す**(第3章の代償。本数分だけ木の更新が発生する)
5. `innodb_flush_log_at_trx_commit = 2`(**失ってよいデータのみ**)

⚠️ ただし **1トランザクションを大きくしすぎない**でください。100万件を1トランザクションにすると、undo が肥大化し、ロールバックが地獄になり、後述のロック問題も起きます。**1,000〜10,000件ごとにコミット**が現実的な落としどころです。

### ② 長すぎるトランザクションは害悪

この章と次章の両方から、同じ結論が出ます。

- undo ログが溜まる(History list length が伸びる)
- ロールバックが長引く
- **ロックを持ち続ける**(第5章)

だから **トランザクションは短く**。特にやってはいけないのが、

```kotlin
transaction {
    val order = orderRepository.insert(...)
    paymentApi.charge(order)          // ❌ 外部APIの呼び出し
    orderRepository.updateStatus(...)
}
```

外部 API が遅ければ、その間ずっとトランザクションが開き、ロックを握り続けます。**Phase 3 でやった「ネットワークは失敗する前提」**を思い出してください。相手が30秒返さなければ、30秒間ロックが解放されません。

**原則: トランザクションの中でネットワーク I/O を待たない。** 第6章と第8章で、この設計を具体的に扱います。

### ③ DDL は暗黙コミットする(MySQL の罠)

```sql
START TRANSACTION;
INSERT INTO orders (...) VALUES (...);
CREATE TABLE tmp (id INT);      -- ← ここで暗黙的に COMMIT される!
ROLLBACK;                        -- INSERT は戻らない
```

`CREATE` / `ALTER` / `DROP` / `TRUNCATE` などの DDL は、**実行時に現在のトランザクションを暗黙でコミットします**。「マイグレーションをトランザクションで囲んだから失敗しても安全」という前提は、**MySQL では成り立ちません**。

> PostgreSQL は DDL もトランザクションに含められるので、ここは移行時にハマる差分です。MySQL 8 で DDL 自体は原子的になりました(1つの `ALTER` が半端に終わることはない)が、**他の文と一緒にロールバックすることはできません**。

実務では、マイグレーションツール(Flyway 等)を使い、**1ファイル1 DDL**に分けて、失敗時は前進あるのみ(修正マイグレーションを足す)という運用が基本になります。

## 演習

### 演習1 — `fsync` 回数を数える

次の3つのコードで、`fsync` は何回発生するか(グループコミットは考えないものとする)。

```
A) autocommit=ON で INSERT を1000回実行
B) START TRANSACTION → INSERT 1000回 → COMMIT
C) START TRANSACTION → INSERT 100回 → COMMIT を10セット
```

<details>
<summary>解答</summary>

`sync_binlog=1` も考えると、コミット1回につき redo と binlog で **2回**の `fsync` が発生します。

| | コミット回数 | fsync 回数(概算) |
|---|---|---|
| A | 1000 | 2000 |
| B | 1 | 2 |
| C | 10 | 20 |

**A と B では1000倍の差**です。4.4 の実測で数十倍にとどまったのは、グループコミットや OS 側の最適化が効いているためですが、桁が違うことに変わりはありません。

**では B が最善か?** そうとは限りません。1000件なら B で問題ありませんが、100万件なら B は undo が肥大化し、ロールバックが長く、ロックも長時間保持します。**C の形(適度な単位で区切る)が実務の答え**です。「大きすぎず、小さすぎず」を意識してください。
</details>

### 演習2 — 障害シナリオを考える

`innodb_flush_log_at_trx_commit = 2` を設定したシステムがあります。次の3つのケースで、直近1秒間のコミット済みデータはどうなりますか。

1. MySQL のプロセスが OOM Killer に殺された
2. サーバの電源が突然落ちた
3. `docker compose stop` で正常に停止した

<details>
<summary>解答</summary>

**1. 失われません。**
値 2 は「ログをファイルに `write` はするが `fsync` はしない」動作です。`write` した時点でデータは **OS のページキャッシュ**に渡っています。MySQL プロセスが死んでも OS は生きているので、OS がディスクに書き出してくれます。

**2. 失われる可能性があります(最大約1秒分)。**
OS のページキャッシュはメモリ上にあるので、電源断で消えます。**コミット成功を返したのにデータが無い**、という状態が起こり得ます。

**3. 失われません。**
正常終了時は全てフラッシュされます。

**この違いが値 2 の設計思想です。** 「アプリのバグやプロセスクラッシュには耐えるが、ハードウェア障害には耐えない」という中間的な保証です。クラウドの仮想マシンで「ホストごと落ちる」ことがどれくらいあるかを考えて判断することになります。

**なお `docker compose kill` は 2 に近い**(プロセスを SIGKILL するだけで OS は生きている)ので、4.6 の実験では値 2 でもデータは残ります。本当の電源断を再現するのは、コンテナでは難しいと覚えておいてください。
</details>

### 演習3 — ロールバックを測る

大量更新のロールバックにかかる時間を実測してください。

```sql
START TRANSACTION;
UPDATE orders SET status = 'test';   -- 50万行
-- 経過時間を記録
ROLLBACK;
-- 経過時間を記録
```

そのうえで、「本番で長時間バッチを KILL するとき、何に注意すべきか」を述べてください。

<details>
<summary>解答例</summary>

ロールバックは UPDATE と同程度、あるいはそれ以上かかることがあります。undo ログを1件ずつ逆適用する実作業だからです。

**KILL 時の注意点**

1. **KILL してもすぐには終わらない**。`SHOW ENGINE INNODB STATUS` の `TRANSACTIONS` セクションで `ROLLING BACK` 状態と残り行数が見られるので、進捗を確認する
2. **待つしかない**。「終わらないから MySQL を再起動しよう」は逆効果で、起動時のクラッシュリカバリで同じロールバックをやり直すことになる(しかもその間、DB 全体が使えない)
3. **ロールバック中もロックは保持されたまま**。他の処理への影響が続く(第5章)
4. **そもそも巨大トランザクションにしない**のが唯一の予防策。バッチは 1,000〜10,000件ごとにコミットし、途中まで進んだ状態から再開できる設計にする

**設計の教訓**: 「途中で止められること」を最初から設計に入れておく。処理済みの位置を記録して再開可能にすれば、KILL は怖くありません。第8章のべき等性の話と繋がります。
</details>

### 演習4 — WAL がなかったら

もし redo ログが存在せず、コミットのたびに変更したページを全てディスクに書いていたとします。

(a) 1つのトランザクションで10ページを更新した場合、書き込み量はどう変わるか
(b) それでも「正しく」動くか。どんな問題が起きるか

<details>
<summary>解答</summary>

**(a)** 10ページ × 16KB = **160KB** を、ディスク上のバラバラの位置に書くことになります。

redo ログなら、変更内容だけなので数百バイト〜数KB を**1箇所に連続で追記**するだけです。**量で数十倍、かつランダム vs シーケンシャルの差**が加わります。

**(b) 正しく動きません。** 致命的な問題があります。

**10ページを書いている途中で電源が落ちたら?** 例えば7ページ目まで書けた状態。これは「トランザクションの一部だけが反映された」状態で、**原子性が壊れています**。しかも「どこまで書けたか」の記録がないので、復旧のしようがありません。

つまり WAL は速度のためだけの工夫ではなく、**原子性を成立させるためにも必要**です。

- ログを先に書く → 「このトランザクションはコミットされた」という**事実が1箇所に記録される**
- ページ本体が中途半端でも、ログを見れば正しい状態に持っていける

**「ログを1回書けばコミット確定」という一点集約**が本質です。分散システムのログレプリケーション(第8章の Raft)も、まったく同じ発想に立っています。
</details>

### 演習5 — 少し難しい

`SHOW ENGINE INNODB STATUS` の `History list length` が 200万まで増えているシステムがあります。

(a) 何が起きていると考えられるか
(b) どう調査するか
(c) どんな症状が出るか

<details>
<summary>解答</summary>

**(a)** **長時間開きっぱなしのトランザクションがある**、が第一候補です。

undo ログは「まだ参照する可能性のあるトランザクションがいる間」はパージできません。誰かが `START TRANSACTION` したまま放置していると、その間に発生した全ての更新の旧値が保持され続けます。

典型的な原因:

- アプリのバグでコミットもロールバックも呼ばれていない
- 対話的なセッションで `BEGIN` したまま人が離席した
- **長時間の分析クエリ**(読み取りだけでも、トランザクションを開いていれば同じ)
- バッチが1トランザクションで長時間動いている

**(b)**

```sql
-- 開始が古い順に並べる
SELECT trx_id, trx_state, trx_started,
       TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS sec,
       trx_rows_modified, trx_query
FROM information_schema.innodb_trx
ORDER BY trx_started;
```

`trx_query` が `NULL` で `trx_started` が古いものが最有力です(**クエリを実行していないのにトランザクションだけ開いている** = 放置されている)。接続元を追うなら `SHOW PROCESSLIST` の `Id` と突き合わせます。

**(c) 症状**

1. **ディスク使用量が増え続ける**(undo テーブルスペースの肥大)
2. **読み取りが遅くなる**。古い版を辿るために undo チェーンを何段も遡る必要が出るため(第5章で詳しくやります)
3. パージが追いつかず、**削除したはずの行の領域が解放されない**
4. 最悪、ディスクフルで停止

**対処**: 原因のトランザクションを `KILL` する。恒久対策としては、アプリ側でトランザクションのタイムアウトを設定し、監視で `History list length` と最古トランザクションの経過秒数にアラートを張ります。**第9章の監視項目リストに入れる値**です。
</details>

## 次章の予告 — 第5章 並行制御

第4章で **A(原子性)と D(耐久性)**が片付きました。残るは **I(分離性)**です。

第1章の実験2を覚えているでしょうか。10スレッドから在庫を1000回減らして、**95個しか減らなかった**やつです。あの問題に、DB がどう答えるのかが次章です。

- 3つのアノマリー(Dirty Read / Non-repeatable Read / Phantom)と**4つの分離レベル**
- **MySQL の既定は REPEATABLE READ**。PostgreSQL(READ COMMITTED)との差が実務で刺さる
- **MVCC** — 4.5 の undo ログが、ここで「読み取りがブロックされない」仕組みとして再登場する
- **ロックの種類**: レコードロック / **ギャップロック / ネクストキーロック**(MySQL 固有の落とし穴)
- 悲観ロックと楽観ロック、`SELECT ... FOR UPDATE`、`SKIP LOCKED`
- **実測**: 2セッションを並走させて、アノマリーとデッドロックを**実際に再現する**
- `SHOW ENGINE INNODB STATUS` のデッドロックログの読み方

第5章は**2つのターミナルを並べて**進めます。手を動かす量が一番多い章です。
